## 1. 배경

지금 하루여행에서 여행은 **완전히 개인 소유**입니다. `trips` · `trip_items` 의 RLS
정책이 `auth.uid() = user_id` 하나뿐이라, 하루 동선을 남이 볼 방법이 아예 없습니다.
공유라고 부를 만한 기능은 방문 인증(`VisitShareSheet`) 하나뿐인데, 이건 "장소 한 곳
다녀왔다"를 OS 공유 시트로 내보내는 것이지 *동선*을 넘기는 게 아닙니다.

동선을 **만드는** 흐름은 이미 다 있습니다 — 여행 일정 설정(TRIP-02-01), 방문 제약
조건(TRIP-02-02), 타임라인(TRIP-03-01), 동선 최적화(TRIP-03-02). 없는 건 그다음입니다.
**잘 짠 하루를 남에게 넘길 방법이 없고, 남이 짜 놓은 하루를 가져올 방법이 없습니다.**

그리고 지금은 **넘겨줄 하루 자체가 없습니다.** 서비스를 처음 연 사람이 보는 건 빈
여행 목록입니다. 재수집으로 장소는 15,518곳이 됐지만 장소가 많다고 하루가 짜이지는
않습니다. 누군가 먼저 "성수동 반나절" 같은 완성된 하루를 놓아 줘야 합니다. 초기에
그 누군가는 사용자가 아니라 **운영자**입니다.

카탈로그 사정도 같은 방향을 가리킵니다. TourAPI 장소의 `source_rating` 은 전부
null 이고 `tags` 도 비어 있습니다. AI 추천(MAP-04-02) 점수식이 평점 항을 쓰는데 그
항이 통째로 비어 있어, 추천은 취향 태그 매칭과 시간대/날씨 보너스에만 기대고
있습니다. **사람이 실제로 짜고 실제로 담아 간 플랜은 이 비어 있는 신호를 메울 가장
현실적인 재료입니다.** 어떤 조합이 실제로 선택되는지는 공공데이터가 주지 않습니다.

## 2. 목표

1. **운영자가 완성된 하루 플랜을 직접 올릴 수 있다** — 원본 여행 없이, 카탈로그
   장소를 골라 순서대로 엮어서.
2. 사용자가 자기 여행을 **공용 플랜으로 올릴** 수 있다.
3. 누구나 공용 플랜을 둘러보다 **한 번의 탭으로 내 여행으로 가져올** 수 있다.

### 성공 기준 (출시 4주 후)

| 지표 | 목표 |
|---|---|
| 운영자 큐레이션 플랜 | 지역 상위 10곳에 각 1개 이상 (서울은 구 단위 5개 이상) |
| 사용자가 올린 공용 플랜 | 50개 이상 |
| 여행을 1개 이상 만든 사용자 중 올린 비율 | 15% 이상 |
| 플랜 상세를 본 사람 중 담기 전환율 | 20% 이상 |
| 담아 간 플랜 중 실제 방문(`visited`)이 1건 이상 발생한 비율 | 30% 이상 |

마지막 지표가 핵심입니다. 담기만 하고 안 가면 이 기능은 북마크일 뿐입니다.

## 3. 범위

### 포함

- 운영자가 공용 플랜을 직접 작성 · 수정 · 내림
- 사용자가 자기 여행을 공용 플랜으로 올리기 / 내리기
- 공용 플랜 리스트 · 상세 · 지역/동행/이동수단 필터
- 공용 플랜을 내 여행으로 담기(복제)
- 신고 · 숨김 (최소 수준)

### 제외 (Non-goals) **[확정]**

- **사용자의 새 장소 직접 등록** — 이번 범위에서 뺍니다. 기존 카탈로그 안에서만
  플랜을 만들고 공유합니다. 이유는 4번에 따로 적습니다.
- 좋아요 · 댓글 · 팔로우 — 소셜 그래프를 만들기 시작하면 다른 서비스가 됩니다.
- 플랜 공동 편집 · 실시간 동기화
- 플랜 커버 사진 업로드 — 1단계는 플랜에 담긴 장소 사진을 그대로 씁니다.
- 플랜 수익화 · 유료 플랜

## 4. 장소 등록을 이번에 넣지 않는 이유 **[확정]**

"카탈로그에 없는 가게를 넣고 싶다"는 요구는 실재하고 언젠가는 해야 합니다. 다만
이번 릴리스에 같이 넣으면 공유 기능 자체가 훨씬 무거워집니다.

- `places` 는 지금 **읽기 전용 공개 카탈로그**입니다. insert 를 여는 순간 `source` ·
  `created_by` · `visibility` 컬럼과 새 RLS 정책이 따라오고, TourAPI 행이 사용자
  편집으로 오염되지 않게 막는 장치도 필요합니다.
- 같은 가게가 여러 행으로 들어오는 중복 등록과 부적절한 등록에 대한 검수 부담이
  새로 생깁니다. 지금 검수 대상은 텍스트 몇 줄뿐인데, 장소를 열면 좌표·주소·사진까지
  사람이 봐야 합니다.
- 재수집으로 전국 229개 시군구에 15,518곳이 들어왔습니다. **"담을 게 없어서" 직접
  등록해야 하는 상황이 이전만큼 흔하지 않습니다.** 정말 부족한지는 이 기능을 켜 보고
  "담을 게 없어 이탈한" 지역·카테고리 데이터로 판단하는 편이 낫습니다.

반대로 **이번 범위를 카탈로그 장소로 한정하면 이 문제들이 전부 사라집니다.** 공용
플랜에 담긴 장소는 이미 `places` 에 있고 이미 비로그인 읽기가 허용된 행이라,
공유받은 사람에게 장소가 안 보이는 경우가 원천적으로 없습니다.

## 5. 핵심 개념 — `trip_items` 와 같은 모양의 공용 테이블 **[확정]**

이 기능의 중심은 화면이 아니라 **`trip_items` 의 공용 짝**입니다.

지금 하루 동선은 `trip_items` 한 테이블에만 존재하고, 그 행은 반드시 한 사용자의
`trips` 에 매달려 있습니다. 여기에 `shared_plan_items` 를 **같은 모양으로** 하나 더
둡니다. 소유자가 없고, 개인 기록이 없고, 누구나 읽을 수 있는 동선입니다.

| | `trip_items` (개인) | `shared_plan_items` (공용) |
|---|---|---|
| 소속 | `trip_id` → 한 사용자의 여행 | `plan_id` → 공용 플랜 |
| 장소 | `place_id` → `places` | `place_id` → `places` (동일) |
| 순서 | `sort_order` | `sort_order` (동일) |
| 시각 | `planned_time` | `planned_time` (동일) |
| 개인 기록 | `status` · `note` · `rating` | **없음**. 대신 공개용 한 줄 팁 |

같은 모양이라는 게 핵심입니다. 두 방향의 변환이 대칭이 되고, 양쪽 다 기계적인
컬럼 대응으로 끝납니다.

```
개인 여행 ──── 올리기(발행) ────→ 공용 플랜
trip_items                        shared_plan_items
   │  status·note·rating 버림          │
   └──────── 담기(복제) ←──────────────┘
      status=planned, note·rating 비움, trip_date 새로 선택
```

운영자가 직접 만드는 플랜은 **왼쪽 없이 오른쪽만 존재**합니다. 원본 여행이 없으므로
`source_trip_id` 가 null 이고, 그래도 아래쪽 화살표(담기)는 똑같이 동작합니다.
이 대칭 덕분에 "운영자가 만든 플랜"과 "사용자가 올린 플랜"이 리스트·상세·담기에서
같은 코드로 처리됩니다. 다른 건 **출처 표시 하나**뿐입니다.

## 6. 사용자 흐름

### A. 운영자가 플랜을 만든다

원본 여행 없이 빈 상태에서 시작합니다. 남의 여행을 불러오는 입구는 없습니다(7-D7).

```
관리자 화면 → "새 공용 플랜"
  → 제목 · 설명 입력
  → 지역(시/도 + 시군구) · 이동수단 · 동행인 · 시작/종료 시각 선택
  → 장소 검색해서 담기 → ▲▼ 로 순서 조정 → 항목별 시각·한 줄 팁 입력
  → 공개
```

### B. 사용자가 자기 여행을 올린다

```
내 여행 상세(타임라인) → "공용 플랜으로 올리기"
  → 공개용 제목 · 설명 입력 (기본값: 여행 제목)
  → 공개되는 내용 미리보기 (7-D1 표 그대로)
  → 공개 → 링크 생성, Web Share API 로 바로 내보내기 가능
```

### C. 둘러보고 담는다

```
하단 탭 "플랜" → 공용 플랜 리스트
  → 지역 · 동행인 · 이동수단 · 소요시간 필터, 인기순/최신순 정렬
  → 카드 탭 → 플랜 상세 (제목 · 설명 · 장소 순서 · 동선 지도 · 예상 소요시간)
  → "내 여행으로 담기" → 날짜 선택 → 내 여행 생성 완료 → 타임라인으로 이동
```

담은 뒤는 평소의 내 여행과 완전히 같습니다. ▲▼ 로 순서를 바꾸고, 빼고, 동선을
다시 최적화하고, 예약을 걸 수 있습니다. **담기는 편집 가능한 출발점이지 고정된
상품이 아닙니다.**

**담기는 항상 새 여행을 만듭니다 [확정].** 기존 여행에 합치는 경로는 1단계에
넣지 않습니다. 합치기를 허용하면 그 자리에서 정해야 할 게 줄줄이 따라옵니다 —
기존 항목 뒤에 붙일지 시각 순으로 섞을지, 같은 장소가 이미 있으면 어떻게 할지,
`planned_time` 이 겹치면 누가 밀리는지, 합친 뒤 되돌릴 수 있는지. 새 여행만
만들면 실패해도 **버리면 그만**이고, 합치기가 정말 필요한지는 담기 전환율과
"담은 직후 다른 여행에서 항목을 옮긴" 행동이 알려 줍니다.

## 7. 설계 결정과 근거

### D1. 올리기는 원본 여행의 "라이브 공개"가 아니라 **스냅샷 복사** **[확정]**

`trips` 행에 `is_public` 을 켜서 RLS 를 여는 방식은 만들기는 쉽지만 받아들일 수
없습니다. `trips` 에는 `trip_date`(내가 언제 어디 있었는지)·`companions`(누구와
갔는지)가 있고, `trip_items` 에는 `note`·`rating`(개인 리뷰)과 `status`가 있습니다.
"이 여행 공개"를 켜는 순간 이 전부가 따라 나갑니다. 사용자가 공개하려는 건 *동선*이지
*일기*가 아닙니다.

그리고 운영자가 만드는 플랜에는 애초에 원본 여행이 없습니다. **`trips` 에 플래그를
다는 구조로는 "원본 없는 플랜"을 표현할 수가 없습니다.** 별도 테이블이어야 두 출처가
같은 모양으로 공존합니다.

| 원본 | 공용 플랜에 | 이유 |
|---|---|---|
| `title` | 별도 공개 제목 입력 | 원본 제목은 "엄마 생신 나들이" 같은 사적인 이름일 수 있음 |
| — | **설명(`description`) 새로 입력** | 리스트에서 고를 때 제목만으로는 부족함. 운영자 플랜은 특히 이 칸이 본체 |
| `tour_area_code` · `tour_sigungu_code` | 그대로 | 플랜을 고르는 1순위 기준 |
| `transport`, `start_time`/`end_time` | 그대로 | 소요시간·이동수단 필터의 근거 |
| `trip_date` | **요일·계절만** | 특정 날짜는 위치 이력이 됨 |
| `companions` | 그대로 | 필터 축으로 유용 |
| item `place_id`, `sort_order`, `planned_time` | 그대로 | 이게 플랜의 본체 |
| item `note`, `rating`, `status` | **제외** | 개인 리뷰. 대신 공개용 한 줄 팁을 새로 받음 |

부작용: 원본을 고쳐도 공용 플랜은 안 바뀝니다. 관리 화면에 "원본이 수정됨 · 다시
올리기" 배너를 띄워 사용자가 명시적으로 갱신하게 합니다. 이 편이 "내가 여행 날짜를
바꿨더니 공개된 플랜도 조용히 바뀌어 있는" 것보다 낫습니다.

### D2. 출처는 컬럼 하나로 구분한다 — 테이블을 나누지 않는다 **[확정]**

운영자 플랜과 사용자 플랜을 다른 테이블에 두면 리스트·상세·담기·신고가 전부 두 벌이
됩니다. `origin` 컬럼 하나(`admin` / `user`)로 구분하고 나머지는 전부 공유합니다.

- 리스트·상세·담기 쿼리는 `origin` 을 모릅니다. 화면에서 배지만 다르게 붙입니다.
- 운영자 플랜은 `author_user_id` 가 null 이고 작성자 자리에 "운영자"를 표시합니다.
- 수정 권한만 갈립니다 — `origin='user'` 는 작성자 본인, `origin='admin'` 은 관리자.

작성자 닉네임 노출은 7-D8 에서 따로 다룹니다.

### D3. 이 기능은 `places` 를 건드리지 않는다 **[확정]**

공용 플랜의 모든 항목은 `places` 의 기존 행을 가리킵니다. `places` 는 이미
`using (true)` 로 비로그인 읽기가 열려 있어, 공유받은 사람이 로그인하지 않아도
장소 이름·사진·주소·좌표가 전부 보입니다. **공유 기능 때문에 `places` 스키마나 정책이
바뀌는 일은 없습니다.**

주의할 점 하나: `shared_plan_items.place_id` 는 `places` 를 참조하므로, 재수집으로
장소가 사라지면 플랜에 구멍이 납니다. **항목만 조용히 지우면 순서가 어그러진 플랜이
그대로 공개돼 있게 됩니다** — 3곳짜리 플랜이 2곳이 되고, 아무도 모릅니다. 반대로
FK 를 `restrict` 로 걸면 이번엔 **재수집 배치가 장소를 지우지 못해 통째로 실패**합니다.
카탈로그 갱신이 공유 기능 때문에 막히는 건 순서가 뒤바뀐 것입니다.

그래서 **`on delete cascade` 는 유지하되, 항목이 그렇게 사라지면 부모 플랜을 자동으로
내립니다** **[확정]**. `shared_plan_items` 의 after-delete 트리거가
`shared_plans.is_hidden = true` 와 `hidden_reason = 'place_removed'` 를 씁니다.
관리자 화면(SHARE-06-06)은 이 사유로 내려간 플랜을 따로 모아 보여 주고, 관리자가
장소를 갈아 끼우거나 플랜을 지웁니다. 배치는 막히지 않고, 깨진 플랜은 공개되지 않고,
누가 손봐야 하는지는 남습니다.

### D4. 담기는 "복제"이지 "참조"가 아니다 **[확정]**

담으면 `trips` + `trip_items` 가 내 소유로 새로 생깁니다. 원본 플랜이 내려가도,
작성자나 운영자가 수정해도 내 여행은 그대로입니다. 참조 방식이면 남이 내 여행 내용을
바꿀 수 있게 되는데, 이미 예약(`reservations`)이 트립 항목에 걸리는 구조라 위험합니다.

복제 시 초기화 규칙: `status` 는 전부 `planned`, `note`·`rating` 은 비움,
`trip_date` 는 담는 사람이 새로 선택, `planned_time` 은 플랜의 시작 시각을 기준으로
상대 간격을 유지해 다시 계산.

### D5. 담은 수 카운트는 RPC 로 **[확정]**

인기순 정렬을 하려면 `shared_plans.clone_count` 가 필요한데, RLS 아래에서 사용자는
남의 행을 update 할 수 없습니다. `security definer` 함수 하나로 "담기"를 처리하면서
카운트를 올립니다. 클라이언트에서 update 를 시도하다 조용히 실패하는 구조를 만들지
않기 위한 것입니다.

카탈로그의 `source_rating` 이 전부 null 이라 장소 평점으로는 아무것도 정렬할 수
없습니다. **담은 수가 이 서비스의 첫 번째 인기 신호가 됩니다.**

### D6. 관리자 판별은 `profiles.role` **[확정]**

지금 `profiles` 에는 역할 개념이 없습니다(`id` · `nickname` · `taste_tags` ·
`created_at` 뿐). **`profiles.role` 컬럼**(`user` / `admin`, 기본 `user`)을 추가하고,
`security definer` 인 **`is_admin()`** 함수 하나로 판정합니다.

`is_admin()` 이 `security definer` 여야 하는 이유: RLS 정책 안에서 `profiles` 를 다시
select 하면 `profiles` 자신의 RLS 가 또 평가되면서 무한 재귀로 막힙니다. 정의자
권한으로 도는 함수로 감싸 이 고리를 끊습니다. 함수 안에서는 `auth.uid()` 로 자기 행
하나만 보고 `search_path` 를 고정합니다.

별도 `admins` 테이블이나 JWT claim 을 쓰지 않는 이유: 테이블을 하나 더 두면 조인이
하나 더 붙고, JWT claim 은 권한을 바꿀 때 토큰이 갱신될 때까지 반영되지 않습니다.
관리자 수가 한 자릿수인 단계에서는 컬럼 하나가 맞습니다.

관리자 지정은 화면으로 만들지 않습니다. **SQL 로 직접 `role` 을 바꿉니다** — 관리자를
임명하는 화면 자체가 가장 위험한 공격면이고, 지금 필요하지도 않습니다.

### D7. 관리자는 남의 **비공개** 여행을 가져올 수 없다 **[확정]**

"개인 `trip_items` 를 가져온다"에는 두 가지가 섞여 있습니다. 하나는 **사용자 본인이
자기 여행을 올리는 것**이고, 다른 하나는 **관리자가 남의 여행을 꺼내 오는 것**입니다.
앞의 것만 허용합니다.

`trips` 에는 `trip_date` 가 있고 `trip_items` 에는 방문한 장소와 시각이 있습니다.
이 둘을 합치면 **그 사람이 언제 어디에 있었는지의 기록**입니다. 운영자가 좋은 동선을
찾겠다고 이걸 들여다볼 수 있게 만드는 건, 기능의 이득에 비해 대가가 너무 큽니다.
한 번 열면 "관리자는 모든 여행을 볼 수 있다"가 시스템의 성질이 되고, 이후의 모든
권한 사고가 여기서 출발합니다.

그래서 `trips` · `trip_items` 의 RLS 는 **지금 그대로 `auth.uid() = user_id` 하나로
둡니다.** 관리자라도 예외가 없습니다. 관리자가 다룰 수 있는 것은:

- 자기가 만든 `origin='admin'` 플랜 — 작성 · 수정 · 삭제
- 사용자가 **이미 올린** `origin='user'` 플랜 — 숨김 · 복구 · 신고 처리

좋은 사용자 동선을 큐레이션에 쓰고 싶다면, 이미 공용으로 올라온 플랜을 **담아서**
자기 계정의 여행으로 만든 뒤 다듬어 `origin='admin'` 으로 다시 올리면 됩니다.
일반 사용자와 똑같은 경로를 쓰는 것이고, 별도 권한이 필요 없습니다.

### D8. 작성자 닉네임은 뷰로 노출한다 **[확정]**

사용자 플랜에는 작성자 닉네임을 **노출합니다**. 누가 짰는지 모르는 동선은 고를 근거가
없고, 올린 사람 입장에서도 이름이 남지 않으면 올릴 이유가 줄어듭니다.

다만 `profiles` 에 `using (true)` select 정책을 그냥 여는 건 안 됩니다. `profiles`
에는 `taste_tags`(취향 이력)가 같이 있고, 정책을 열면 **가입자 전원의 닉네임 목록을
긁을 수 있게** 됩니다. RLS 는 행 단위라 컬럼을 가려 주지도 않습니다.

그래서 **뷰 하나만 공개**합니다.

```
public.public_profiles = (id, nickname)
  단, 공개된 플랜(is_hidden = false)을 하나 이상 올린 사용자만
```

노출 범위가 "공용 플랜을 올린 사람"으로 좁혀지고, `taste_tags` 는 애초에 뷰에
없습니다. `profiles` 본체의 정책은 지금 그대로 둡니다.

운영자 플랜은 `author_user_id` 가 null 이므로 이 뷰를 타지 않고 "운영자"로 고정
표시합니다. **플랜별 익명 올리기는 2단계로 미룹니다** — 컬럼 하나와 화면 분기가
붙는데, 익명 수요가 실제로 있는지는 아직 모릅니다.

## 11. 품질 · 어뷰징

최소한으로 갑니다. 지금 사용자 규모에서 정교한 검수 시스템은 과합니다. 장소를
사용자가 만들지 않으므로 검수 대상은 **플랜의 제목·설명·한 줄 팁 텍스트뿐**입니다.

- **신고** — 플랜 상세에 신고 버튼. 같은 플랜에 서로 다른 사용자의 신고가 3건
  쌓이면 `is_hidden` 을 **자동 전환**하고 `hidden_reason = 'reported'` 를 남깁니다.
  **되살리는 건 관리자가 수동으로** 합니다 **[확정]**.
  자동 숨김만 두고 복구를 자동화하지 않는 이유는 비대칭이 맞기 때문입니다. 잘못
  숨긴 플랜의 피해는 "안 보인다" 한 줄이고, 잘못 남겨 둔 플랜의 피해는 그동안
  그걸 본 모든 사람에게 갑니다. 사람이 붙어야 하는 쪽은 **되살릴 때**입니다.
  신고는 사용자당 플랜당 1건으로 제한합니다 — 안 그러면 혼자 3번 눌러 남의 플랜을
  내릴 수 있습니다.
- **운영자 플랜은 신고 대상에서 제외하지 않습니다.** 운영자도 틀립니다. 다만 자동
  숨김은 걸지 않고 관리자 화면에만 올립니다.
- **공개 취소** — 작성자와 관리자는 언제든 내릴 수 있고, 이미 담아 간 사람의 여행은
  그대로 남습니다(복사본이므로).
- **공개 최소 조건** — 장소가 2곳 미만인 플랜은 올릴 수 없습니다. 한 곳짜리는
  플랜이 아니라 즐겨찾기입니다. 제목과 설명은 둘 다 필수입니다.
- **아직 다녀오지 않은 여행도 올릴 수 있습니다 [확정].** 방문 1건 이상을 요구하면
  가장 좋은 재료가 막힙니다 — 잘 짠 동선은 다녀오기 *전에* 완성돼 있고, 다녀온
  뒤에는 올릴 동기가 식습니다. 무엇보다 **운영자 플랜은 원래 아무도 안 다녀온
  플랜**이라, 방문을 조건으로 걸면 이 문서의 목표 1번과 정면으로 부딪칩니다.
  대신 리스트 카드에 **"다녀옴" 배지**를 붙여 구분합니다 — `trip_items.status` 에
  `visited` 가 하나라도 있는 여행에서 올라온 플랜입니다. 검증된 동선을 찾는 사람은
  이 배지로 거르면 됩니다.

  조정합니다. 드래그 앤 드롭은 쓰지 않습니다. 관리자 작성 화면(SHARE-06-05)도
  같은 ▲▼ 방식입니다.
- 플랜 리스트 카드는 한 손 스크롤로 훑을 수 있는 높이로. 지도는 상세에서만 띄웁니다.
- 설명은 리스트 카드에서 두 줄로 자르고 상세에서 전문을 보여 줍니다.
- 사용자 대면 문구에 "하루트립"이 들어가지 않게 합니다.

## 14. 수용 기준

괄호 안은 그 기준의 근거가 적힌 본문 위치입니다.

- [ ] 관리자가 원본 여행 없이 공용 플랜을 만들 수 있고, 그 플랜의 `source_trip_id` 가 null 이다
- [ ] 관리자가 만든 플랜과 사용자가 올린 플랜이 리스트·상세·담기에서 같은 코드로 처리되고, 화면 배지만 다르다
- [ ] 내 여행을 올려도 `trip_date`·`note`·`rating` 이 공용 플랜에 들어가지 않는다 (공용 플랜 직접 조회로 확인)
- [ ] 제목과 설명이 비어 있으면 올리기·작성 버튼이 비활성이다
- [ ] 비로그인 상태에서 공유 링크를 열면 플랜과 장소 정보가 전부 보이고, 담기를 누를 때만 로그인으로 간다
- [ ] 담아 간 여행의 항목은 전부 `planned` 상태이고 남의 리뷰가 딸려 오지 않는다
- [ ] 담은 뒤 ▲▼ 로 순서를 바꾸고 동선 최적화를 다시 돌릴 수 있다
- [ ] 작성자나 관리자가 플랜을 내려도 이미 담아 간 사람의 여행은 그대로 열린다
- [ ] 원본 여행을 수정하면 관리 화면에 "다시 올리기" 배너가 뜬다
- [ ] 일반 사용자가 `origin='admin'` 플랜을 update·delete 하려는 시도가 RLS 에서 막힌다
- [ ] 일반 사용자가 남의 `shared_plans` 행을 직접 update·delete 하려는 시도가 RLS 에서 막힌다
- [ ] 관리자가 아닌 계정으로 `/admin/plans` 에 직접 접근하면 막힌다
- [ ] 관리자 계정으로도 남의 `trips`·`trip_items` 를 select 할 수 없다 (7-D7)
- [ ] `is_admin()` 을 쓰는 정책이 `profiles` RLS 재귀에 걸리지 않는다
- [ ] 담기를 여러 번 해도 `clone_count` 가 정확히 그만큼만 오른다
- [ ] 장소가 1곳인 플랜은 올리기 버튼이 비활성이다 (11번)
- [ ] 같은 사용자가 같은 플랜을 여러 번 신고해도 1건으로만 집계된다 (11번)
- [ ] 한 번도 방문하지 않은 여행도 올릴 수 있고, 카드에 "다녀옴" 배지가 붙지 않는다 (11번)
- [ ] `public_profiles` 뷰에 공개 플랜이 없는 사용자의 닉네임이 나오지 않고, `taste_tags` 는 어떤 경로로도 새어 나가지 않는다 (7-D8)
- [ ] 플랜에 담긴 장소를 지우면 그 플랜이 자동으로 내려가고 `hidden_reason='place_removed'` 가 기록된다 (7-D3)
- [ ] 장소 삭제가 공유 테이블 때문에 막히지 않는다 — 재수집 배치가 그대로 돈다 (7-D3)
- [ ] 375px 폭에서 하단 탭 6개의 라벨이 잘리거나 줄바꿈되지 않고, 터치 타깃이 44px 이상이다 (8번)
- [ ] 데모 모드(`.env` 없음)에서 리스트·상세·담기가 모두 동작하고, 운영자 플랜과 사용자 플랜이 둘 다 보인다
- [ ] `npx tsc --noEmit` · `npm run build` 통과
- [ ] 검증에 쓴 테스트 계정과 그 계정이 만든 행만 정확히 지정해 삭제했고, 실제 사용자 데이터는 그대로다

## 15. 단계

1. **1단계** — 공용 테이블 + 관리자 작성 + 사용자 올리기 + 리스트 / 상세 / 담기 /
   신고. 이 문서의 범위.
2. **2단계** — 공용 플랜을 AI 추천 피드(MAP-04-02)에 섞기, 담은 수 기반 장소
   인기도 산출 (비어 있는 `places.source_rating` 을 대체할 신호).

   **1단계에는 넣지 않습니다 [확정].** 추천 피드는 지금 장소 단위로 점수를 매기는데
   플랜은 장소 묶음이라, 둘을 한 화면에 섞으려면 점수식을 공통 단위로 다시 짜야
   합니다. 그보다 결정적인 건 **재료가 없다는 것**입니다. 출시 직후 공용 플랜은
   운영자가 넣은 몇 개뿐이고 `clone_count` 는 전부 0입니다. 0으로 정렬된 것을
   추천이라고 부를 수는 없습니다. 담은 수가 쌓인 뒤에 섞습니다.
3. **3단계** — 사용자 장소 직접 등록을 별도 intent 로 재검토. 1단계에서 "담을 게
   없어 이탈한" 지역·카테고리 데이터를 근거로 판단.

## 16. 확인이 필요한 사실

- **카탈로그만으로 공유할 만한 플랜이 나오는지** — 확인됐습니다. 재수집 후 시군구
  229개 중 228개가 장소 10곳 이상이고, 서울은 25개 구가 전부 들어왔습니다. 이전
  문서에 적혀 있던 "리프 115개 중 5곳 이상이 17개뿐"은 더 이상 사실이 아닙니다.
- **상세 수집이 안 끝나도 되는지** — 이 기능이 쓰는 값(이름·카테고리·주소·좌표·사진)은
  목록 응답에서 이미 전부 채워져 있습니다. 상세가 채우는 건 영업시간·전화·소개이고
  이건 비면 화면에서 숨기는 값입니다. **상세 완료를 기다릴 이유는 없어 보입니다.**
  다만 운영자 큐레이션 플랜을 만들 때는 영업시간이 있어야 순서를 제대로 짤 수
  있으므로, 큐레이션 대상 지역은 상세가 찬 곳부터 고르는 편이 낫습니다.
- 담기 시 `planned_time` 재계산 규칙이 원본과 담는 사람의 `start_time` 이 다를 때
  어색해지지 않는지 (예: 원본 09:00 시작 → 담는 사람 13:00 시작)
- `trip_items` 가 realtime publication 에 올라가 있는데, 담기로 여러 행을 한 번에
  넣을 때 타임라인 화면이 깜빡이지 않는지
- 미판정(`tour_sigungu_code = -1`) 장소 30곳이 공용 플랜에 담기지 않게 막혀 있는지
  (`db.ts` 의 `.gte('tour_sigungu_code', 0)` 필터가 플랜 항목 조회에도 걸리는지)
