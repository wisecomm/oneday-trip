## 1. 배경

지금 하루여행에서 여행 플랜은 **완전히 개인 소유**입니다. `trips` · `trip_items` 의
RLS 정책이 `auth.uid() = user_id` 하나뿐이라, 내가 만든 하루 동선을 남이 볼 방법이
아예 없습니다. 공유라고 부를 만한 기능은 방문 인증(`VisitShareSheet`) 하나뿐인데,
이건 "장소 한 곳 다녀왔다"를 OS 공유 시트로 내보내는 것이지 *플랜*을 넘기는 게
아닙니다.

플랜을 **만드는** 흐름은 이미 다 있습니다 — 여행 일정 설정(TRIP-02-01), 방문 제약
조건(TRIP-02-02), 타임라인(TRIP-03-01), 동선 최적화(TRIP-03-02), 생성 시 추천 5곳
자동 담기까지. 없는 건 만든 다음입니다. **다 짜 놓은 하루를 남에게 넘길 방법이 없고,
남이 짜 놓은 하루를 가져올 방법이 없습니다.**

여기에 카탈로그 사정이 하나 더 겹칩니다. README 가 정직하게 적어 둔 대로 TourAPI
장소 339곳은 `rating` 이 전부 0이고 `tags` 가 전부 비어 있습니다. AI 추천(MAP-04-02)
점수식이 `rating × 2` 를 기본 점수로 쓰는데 그 항이 통째로 0이라, 추천은 취향 태그
매칭과 시간대/날씨 보너스에만 기대고 있습니다. **사람이 실제로 짜고 실제로 다녀온
플랜은 이 비어 있는 신호를 메울 가장 현실적인 재료입니다.** 어떤 조합이 실제로
선택되는지는 공공데이터가 주지 않는 정보입니다.

## 2. 목표

1. 사용자가 자기 하루 플랜을 **공개**하고 링크로 넘길 수 있다.
2. 사용자가 남의 플랜을 둘러보다 **한 번의 탭으로 내 여행으로 가져올** 수 있다.

### 성공 기준 (출시 4주 후)

| 지표 | 목표 |
|---|---|
| 공개된 플랜 수 | 50개 이상 |
| 여행을 1개 이상 만든 사용자 중 공개한 비율 | 15% 이상 |
| 플랜 상세를 본 사람 중 담기 전환율 | 20% 이상 |
| 담아 간 플랜 중 실제 방문(`visited`)이 1건 이상 발생한 비율 | 30% 이상 |

마지막 지표가 핵심입니다. 담기만 하고 안 가면 이 기능은 북마크일 뿐입니다.

## 3. 범위

### 포함

- 내 여행을 공개 플랜으로 내보내기 / 내림
- 공개 플랜 리스트 · 상세 · 지역/동행/이동수단 필터
- 공개 플랜을 내 여행으로 담기(복제)
- 신고 · 숨김 (최소 수준)

### 제외 (Non-goals) **[확정]**

- **사용자의 새 장소 직접 등록** — 이번 범위에서 뺍니다. 기존 카탈로그 339곳
  안에서만 플랜을 만들고 공유합니다. 뺀 이유는 아래 4번에 따로 적습니다.
- 좋아요 · 댓글 · 팔로우 — 소셜 그래프를 만들기 시작하면 다른 서비스가 됩니다.
- 플랜 공동 편집 · 실시간 동기화
- 플랜 커버 사진 업로드 — 1단계는 플랜에 담긴 장소 사진을 그대로 씁니다.
- 플랜 수익화 · 유료 플랜

## 4. 장소 등록을 이번에 넣지 않는 이유 **[확정]**

"카탈로그에 없는 가게를 넣고 싶다"는 요구는 실재하고 언젠가는 해야 합니다. 다만
이번 릴리스에 같이 넣으면 공유 기능 자체가 훨씬 무거워집니다.

- `places` 는 지금 **읽기 전용 공개 카탈로그**입니다. insert 를 여는 순간 `source` ·
  `created_by` · `visibility` 컬럼과 새 RLS 정책이 따라오고, TourAPI 행이 사용자
  편집으로 오염되지 않게 막는 장치도 필요합니다.
- `places.region` 은 `regions.name` 을 참조하는 FK 인데 등록된 지역은 전국 시/도의
  *일부* 구/시뿐입니다. 사용자가 등록 안 된 지역 좌표를 넣으면 저장이 FK 위반으로
  실패하므로, 좌표→지역 자동 매핑과 그 예외 처리를 먼저 설계해야 합니다.
- 중복 등록(같은 가게가 여러 행)과 부적절한 등록에 대한 검수 부담이 새로 생깁니다.

반대로 **이번 범위를 카탈로그 장소로 한정하면 이 문제들이 전부 사라집니다.** 공개
플랜에 담긴 장소는 이미 `places` 에 있고 이미 비로그인 읽기가 허용된 행이라,
공유받은 사람에게 장소가 안 보이는 경우가 원천적으로 없습니다. 플랜 공유는
`shared_plans` 두 테이블만 추가하면 끝납니다.

장소 등록은 공유 기능이 실제로 쓰이는지 본 뒤 별도 intent 로 다룹니다. 그때 "어느
지역·어느 카테고리에서 사용자가 담을 게 없어 이탈했는지"를 이 기능의 데이터로
판단할 수 있으니, 순서도 이쪽이 맞습니다.

## 5. 사용자 흐름

### A. 플랜 공개

```
내 여행 상세(타임라인) → "플랜 공유하기"
  → 공개용 제목 · 한 줄 소개 입력 (기본값: 여행 제목)
  → 공개되는 내용 미리보기 (아래 6-D1 참고)
  → 공개 → 링크 생성, Web Share API 로 바로 내보내기 가능
```

### B. 플랜 둘러보고 담기

```
하단 탭 "플랜" → 공개 플랜 리스트
  → 지역 · 동행인 · 이동수단 · 소요시간 필터, 인기순/최신순 정렬
  → 카드 탭 → 플랜 상세 (장소 순서 · 동선 지도 · 예상 소요시간)
  → "내 여행으로 담기" → 날짜 선택 → 내 여행 생성 완료 → 타임라인으로 이동
```

담은 뒤는 평소의 내 여행과 완전히 같습니다. ▲▼ 로 순서를 바꾸고, 빼고, 동선을
다시 최적화하고, 예약을 걸 수 있습니다. **담기는 편집 가능한 출발점이지 고정된
상품이 아닙니다.**

## 6. 설계 결정과 근거

### D1. 공개는 원본 여행의 "라이브 공개"가 아니라 **스냅샷 복사**

`trips` 행에 `is_public` 을 켜서 RLS 를 여는 방식은 만들기는 쉽지만 받아들일 수
없습니다. `trips` 에는 `trip_date`(내가 언제 어디 있었는지)·`companions`(누구와
갔는지)가 있고, `trip_items` 에는 `note`·`rating`(개인 리뷰)과 `status`가 있습니다.
"이 여행 공개"를 켜는 순간 이 전부가 따라 나갑니다. 사용자가 공개하려는 건 *동선*이지
*일기*가 아닙니다.

그래서 공개 시점에 `shared_plans` · `shared_plan_items` 로 **필요한 것만 복사**합니다.

| 원본 | 공개본에 | 이유 |
|---|---|---|
| `title` | 별도 공개 제목 입력 | 원본 제목은 "엄마 생신 나들이" 같은 사적인 이름일 수 있음 |
| `destination`, `transport`, `start_time`/`end_time` | 그대로 | 플랜을 고르는 기준이 됨 |
| `trip_date` | **요일·계절만** | 특정 날짜는 위치 이력이 됨 |
| `companions` | 그대로 | 필터 축으로 유용 |
| item `place_id`, `sort_order`, `planned_time` | 그대로 | 이게 플랜의 본체 |
| item `note`, `rating`, `status` | **제외** | 개인 리뷰. 대신 공개용 한 줄 팁을 새로 받음 |

부작용: 원본을 고쳐도 공개본은 안 바뀝니다. 상세 화면에 "원본이 수정됨 · 다시
공개하기" 배너를 띄워 사용자가 명시적으로 갱신하게 합니다. 이 편이 "내가 여행 날짜를
바꿨더니 공개된 플랜도 조용히 바뀌어 있는" 것보다 낫다고 봅니다.

### D2. 이 기능은 `places` 를 건드리지 않는다

**선행 작업이 `places` 를 대대적으로 바꾸는 것과는 별개입니다** — 지역 코드 체계
전환과 장소 재수집은 [선행 문서](../2026-09-20-재수집-스키마-교체/intent.md)의 일이고,
여기서 말하는 건 "공유 기능 자체는 `places` 에 손대지 않는다"입니다.

공개 플랜의 모든 항목은 `places` 의 기존 행을 가리킵니다. `places` 는 이미
`using (true)` 로 비로그인 읽기가 열려 있어, 공유받은 사람이 로그인하지 않아도
장소 이름·사진·주소·좌표가 전부 보입니다. **공유 기능 때문에 `places` 스키마나 정책이
바뀌는 일은 없습니다.**

### D3. 담기는 "복제"이지 "참조"가 아니다

담으면 `trips` + `trip_items` 가 내 소유로 새로 생깁니다. 원본 플랜이 내려가도,
작성자가 수정해도 내 여행은 그대로입니다. 참조 방식이면 남이 내 여행 내용을 바꿀 수
있게 되는데, 이미 예약(`reservations`)이 트립 항목에 걸리는 구조라 위험합니다.

복제 시 초기화 규칙: `status` 는 전부 `planned`, `note`·`rating` 은 비움,
`trip_date` 는 담는 사람이 새로 선택, `planned_time` 은 플랜의 시작 시각을 기준으로
상대 간격을 유지해 다시 계산.

### D4. 담은 수 카운트는 RPC 로

인기순 정렬을 하려면 `shared_plans.clone_count` 가 필요한데, RLS 아래에서 사용자는
남의 행을 update 할 수 없습니다. `security definer` 함수 하나로 "담기"를 처리하면서
카운트를 올립니다. 클라이언트에서 update 를 시도하다 조용히 실패하는 구조를 만들지
않기 위한 것입니다.

카탈로그의 `rating` 이 전부 0이라 장소 평점으로는 아무것도 정렬할 수 없습니다.
**담은 수가 이 서비스의 첫 번째 인기 신호가 됩니다.**

## 8. 데이터 모델 변경 (개요)

기존 테이블은 변경 없습니다. 세 개가 새로 생깁니다. 지역은 선행 작업에서 정한
코드 쌍을 그대로 씁니다 — 이름 문자열이 아닙니다.

- `shared_plans` — 작성자, 공개 제목·소개, **목적지(`tour_area_code` +
  `tour_sigungu_code`, 후자가 null 이면 시/도 전체)**, 이동수단, 동행인, 요일/계절,
  시작·종료 시각, 장소 수, 예상 소요시간, `clone_count`, `is_hidden`,
  `source_trip_id`(갱신 판정용), `source_updated_at`
- `shared_plan_items` — 플랜 id, `place_id`(→ `places`), `sort_order`, `planned_time`,
  공개용 한 줄 팁
- `plan_reports` — 신고자, 플랜 id, 사유, 처리 상태

RLS: `shared_plans`·`shared_plan_items` 는 `is_hidden = false` 이면 누구나 select,
insert·update·delete 는 작성자만. 담기는 `security definer` 함수로.

마이그레이션은 CLAUDE.md 규칙대로 `supabase/migrations/` 에 타임스탬프 파일로만
추가하고 `schema.sql` 스냅샷을 함께 갱신합니다.

## 10. 품질 · 어뷰징

공개 가능 조건은 **[미결 Q4]**, 신고 처리 주체는 **[미결 Q5]** 입니다.

최소한으로 갑니다. 지금 사용자 규모에서 정교한 검수 시스템은 과합니다. 장소를
사용자가 만들지 않으므로 검수 대상은 **플랜의 제목·소개·한 줄 팁 텍스트뿐**입니다.

- **신고** — 플랜 상세에 신고 버튼. 같은 플랜에 신고가 3건 쌓이면 `is_hidden` 자동
  전환하고 운영자가 확인.
- **공개 취소** — 작성자는 언제든 내릴 수 있고, 이미 담아 간 사람의 여행은 그대로
  남습니다(복사본이므로).
- **공개 최소 조건** — 장소가 2곳 미만인 여행은 공개할 수 없게 합니다. 한 곳짜리는
  플랜이 아니라 즐겨찾기입니다.

## 11. 모바일 고려

CLAUDE.md 의 원칙을 그대로 따릅니다.

- 공개 플랜 상세에서 장소 순서 확인은 읽기 전용. 담은 *뒤* 내 타임라인에서 ▲▼ 버튼으로
  조정합니다. 드래그 앤 드롭은 쓰지 않습니다.
- 플랜 리스트 카드는 한 손 스크롤로 훑을 수 있는 높이로. 지도는 상세에서만 띄웁니다.
- 사용자 대면 문구에 "하루트립"이 들어가지 않게 합니다.

## 13. 수용 기준

괄호 안의 Qn 은 그 질문이 닫혀야 판정 기준이 확정되는 항목입니다.

- [ ] 내 여행을 공개해도 `trip_date`·`note`·`rating` 이 공개본에 들어가지 않는다 (공개본 직접 조회로 확인)
- [ ] 비로그인 상태에서 공유 링크를 열면 플랜과 장소 정보가 전부 보이고, 담기를 누를 때만 로그인으로 간다
- [ ] 담아 간 여행의 항목은 전부 `planned` 상태이고 남의 리뷰가 딸려 오지 않는다
- [ ] 담은 뒤 ▲▼ 로 순서를 바꾸고 동선 최적화를 다시 돌릴 수 있다
- [ ] 작성자가 공개를 내려도 이미 담아 간 사람의 여행은 그대로 열린다
- [ ] 원본 여행을 수정하면 공개 플랜 관리 화면에 "다시 공개하기" 배너가 뜬다
- [ ] 남의 `shared_plans` 행을 직접 update·delete 하려는 시도가 RLS 에서 막힌다
- [ ] 담기를 여러 번 해도 `clone_count` 가 정확히 그만큼만 오른다
- [ ] 장소가 1곳인 여행은 공개 버튼이 비활성이다 (Q4)
- [ ] 데모 모드(`.env` 없음)에서 리스트·상세·담기가 모두 동작한다
- [ ] `npx tsc --noEmit` · `npm run build` 통과
- [ ] 검증에 쓴 테스트 계정과 그 계정이 만든 행만 정확히 지정해 삭제했고, 실제 사용자 데이터는 그대로다

## 14. 단계

1. **1단계** — 공개하기 / 리스트 / 상세 / 담기 / 신고. 이 문서의 범위.
2. **2단계** — 공개 플랜을 AI 추천 피드에 섞기, 담은 수 기반 장소 인기도 산출
   (비어 있는 `places.rating` 을 대체할 신호).
3. **3단계** — 사용자 장소 직접 등록을 별도 intent 로 재검토. 1단계에서 "담을 게
   없어 이탈한" 지역·카테고리 데이터를 근거로 판단.

## 15. 확인이 필요한 사실

구현 전에 실제로 확인하고 확정할 것들입니다.

- **카탈로그만으로 공유할 만한 플랜이 나오는지.** 현재 115개 리프 중 장소가 5곳
  이상인 곳은 17개뿐이고 서울은 성동구 하나입니다. 이 상태로는 같은 지역 플랜이
  거의 같은 장소 조합으로 수렴합니다 — 선행 작업인
  [재수집](../2026-09-20-재수집-스키마-교체/intent.md)이 끝난 뒤 다시 판단합니다.
- 담기 시 `planned_time` 재계산 규칙이 원본과 담는 사람의 `start_time` 이 다를 때
  어색해지지 않는지 (예: 원본 09:00 시작 → 담는 사람 13:00 시작)
- `trip_items` 가 realtime publication 에 올라가 있는데, 담기로 여러 행을 한 번에
  넣을 때 타임라인 화면이 깜빡이지 않는지
