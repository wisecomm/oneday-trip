# TourAPI 연동 → 디비 갱신 절차

> 작성일: 2026-09-23
> 대상: `intent/2026-09-20-재수집-스키마-교체/` 의 `collect.mjs` · `load.mjs`
> 성격: 실행 순서대로 따라가는 운영 문서. 왜 그렇게 하는지는
> [재수집·스키마 교체 intent](../2026-09-20-재수집-스키마-교체/intent.md) 에 있습니다.

한국관광공사 TourAPI(KorService2)에서 장소를 받아 Supabase 에 반영하기까지는
**네 단계**입니다. 각 단계는 독립적이고, 중간에 멈춰도 다음에 이어서 할 수 있습니다.

```
① 수집          TourAPI → raw/*.json        collect.mjs
② (매핑)        어느 응답이 어느 테이블로 가는지 — 2번
③ 적재 SQL 생성  raw/ → seed.sql + seed.ts   load.mjs
④ DB 적용       seed.sql → Supabase         supabase db push
⑤ 확인          화면·쿼리로 검증
```

**네트워크가 필요한 건 ①과 ④뿐입니다.** ②는 파일만 읽으므로 몇 번을 돌려도
결과가 같고, 판정 로직을 고쳤을 때 API 를 다시 때리지 않아도 됩니다.

## 0. 사전 준비 (처음 한 번)

### 0-1. API 키

공공데이터포털에서 **한국관광공사_국문 관광정보 서비스(KorService2)** 활용신청을
하고 승인되면 인증키가 나옵니다.

받은 키를 수집 폴더의 `.key` 에 한 줄로 넣습니다.

```bash
cd intent/2026-09-20-재수집-스키마-교체
# .key 를 열어 주석 아래에 키를 붙여 넣는다
```

`.key` 는 `.gitignore` 에 있어 커밋되지 않습니다. 무인 실행(1단계 자동화)에는 이
파일이 반드시 있어야 합니다 — 대화형 입력은 쓸 수 없습니다.

> **Encoding / Decoding 두 가지로 발급됩니다.** 스크립트가 `%` 포함 여부로 갈라
> 처리하지만, `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` 가 나면 반대쪽 키로 바꿔
> 보세요. 첫 실행 실패의 가장 흔한 원인입니다.

### 0-2. 일일 호출 한도 확인

마이페이지 > 오픈API > 개발계정 상세보기에서 일일 트래픽을 봅니다.
**실측으로는 2,000 호출** 이었습니다(장소 1,000곳 분량). 전량 수집에 2주쯤
걸리므로, 급하면 운영계정 전환을 신청하세요 — 키가 바뀌는 게 아니라 같은 키의
한도가 올라갑니다.

### 0-3. Supabase 링크

`supabase/.temp` 에 링크 정보가 저장되는데 `.gitignore` 에 있습니다. **클론했거나
그 폴더가 지워졌으면 매번 다시 링크해야 합니다.**

```bash
npx supabase login
npx supabase link --project-ref <프로젝트-ref>
```

`link` 는 **DB 비밀번호**를 묻습니다. 대시보드 Project Settings > Database 에서
확인·재설정할 수 있고, anon key 와는 다른 값입니다.

## 1. 수집 — TourAPI → `raw/`

```bash
cd intent/2026-09-20-재수집-스키마-교체
node collect.mjs                # 전국, 목록 + 상세
node collect.mjs --area 1       # 특정 시/도만 (areaCode)
node collect.mjs --status       # 진행률만 (run-daily.sh --status 와 동일)
```

**첫 실행은 `--area 1` 로 서울만 돌려 보세요.** 키 인코딩과 응답 모양을 몇 십
호출 안에 확인할 수 있고, 잘못됐으면 `raw/` 를 비우고 다시 시작하면 됩니다.

받는 것은 세 가지입니다.

| 오퍼레이션 | 받는 것 | 호출 수 |
|---|---|---|
| `areaCode2` | 시/도·시군구 코드표 | 약 18 |
| `areaBasedList2` | 장소 목록(이름·주소·좌표·사진·분류) | 약 700 |
| `detailCommon2` + `detailIntro2` | 소개·영업시간·전화 | 장소당 2회 |

**상세가 전체의 98%를 차지합니다.** 전국 15,518곳 기준 약 31,000 호출입니다.

### 중단과 재개

한도에 걸리면 스크립트가 리포트를 찍고 종료코드 1로 나갑니다. **정상 동작입니다.**
다음 날 같은 명령을 다시 돌리면 그 자리에서 이어집니다.

- 목록은 시군구 × 콘텐츠타입 단위로 파일을 쓰고, 이미 있으면 건너뜁니다
- 상세는 그 파일 안에서 `contentid` 별로 기록하고 **한 곳을 받을 때마다 저장**
  하므로, 어느 지점에서 죽어도 손실이 없습니다

### 매일 자동으로 이어받기

```bash
./run-daily.sh                  # 한 번 이어받기 (로그는 raw/logs/)
./run-daily.sh --status         # 전체 진행률

cp com.danyoh.oneday-trip.collect.plist ~/Library/LaunchAgents/
launchctl load ~/Library/LaunchAgents/com.danyoh.oneday-trip.collect.plist
```

매일 00:10 에 실행됩니다. **cron 이 아니라 launchd 인 이유**는, 그 시각에 맥북이
잠들어 있으면 cron 은 그날을 통째로 건너뛰지만 launchd 는 깨어날 때 실행하기
때문입니다. 2주짜리 작업에서 이 차이가 며칠을 좌우합니다.

진행 상황은 `raw/logs/summary.txt` 에 실행마다 한 줄씩 쌓입니다.

### 2회차부터는 바뀐 것만

상세 항목마다 수집 시점의 `modifiedtime` 을 `mt` 로 저장해 둡니다. 다시 실행하면
**새로 생겼거나 값이 바뀐 곳의 상세만** 받습니다. 한 해에 갱신되는 비율이 10%
안팎이라, 2회차는 목록 700 + 상세 수천 호출로 끝납니다.

## 2. 어느 응답이 어느 테이블로 가는가

수집은 세 오퍼레이션을 부르고, 그 결과가 **세 테이블**로 갈립니다. 나머지 네
테이블(`profiles`·`trips`·`trip_items`·`reservations`)에는 **API 응답이 한 줄도
들어가지 않습니다** — 전부 사용자가 앱에서 만드는 데이터입니다.

```
areaCode2 (파라미터 없음) ─────→ region_groups   시/도 18행
areaCode2 (areaCode=N) ────────→ regions         시군구 247행
areaBasedList2 ────────┐
detailCommon2 ─────────┼───────→ places          장소 15,518행
detailIntro2 ──────────┘
```

### 2-1. `region_groups` ← `areaCode2`

| 응답 필드 | 컬럼 | 비고 |
|---|---|---|
| `code` | `tour_area_code` | PK |
| `name` | `name` | 축약 규칙 적용 — `경기도`→`경기`, `강원특별자치도`→`강원` |
| — | `lat`, `lng` | **API 가 주지 않는다.** 그 시/도 장소들의 좌표 평균으로 계산 |
| — | `sort_order` | 고정 순서(서울·경기·인천·부산·제주…) |

### 2-2. `regions` ← `areaCode2` + `areaBasedList2`

| 응답 필드 | 컬럼 | 비고 |
|---|---|---|
| `code` | `tour_sigungu_code` | 부모 `tour_area_code` 와 묶어 복합 PK |
| `name` | `name` | 접두어 없이 `성동구` |
| `lDongRegnCd` + `lDongSignguCd` | `ldong_cd` | **장소 응답에서 가져온다.** `areaCode2` 는 주지 않아, 그 시군구 장소들이 보낸 값의 최빈값을 쓴다 |
| — | `lat`, `lng` | 그 시군구 장소들의 좌표 평균 |
| — | `sort_order` | 가나다순 |

장소가 0곳인 시군구는 넣지 않습니다(폐지된 행정구역).

### 2-3. `places` ← 세 오퍼레이션 합본

**목록(`areaBasedList2`)에서 오는 것**

| 응답 필드 | 컬럼 | 비고 |
|---|---|---|
| `contentid` | `id` | PK. 재수집 때 같은 장소를 알아보는 열쇠 |
| `title` | `name` | |
| `contenttypeid` · `cat3` · `lclsSystm2` | `category` | 밥집·카페·술집·명소로 접는다 |
| `areacode` | `tour_area_code` | |
| `sigungucode` | `tour_sigungu_code` | 판정 파이프라인을 거친다(3단계) |
| `addr1` | `address` | |
| **`mapy`** | `lat` | |
| **`mapx`** | `lng` | `mapx` 가 경도다 — 뒤집으면 지도가 통째로 어긋난다 |
| `firstimage` → `firstimage2` | `image_url` | 앞엣것이 없으면 뒤엣것 |
| `modifiedtime` | `source_modified_at` | 재수집이 "바뀐 것만" 받는 근거 |
| `lDongRegnCd`·`lDongSignguCd` | — | `places` 에는 넣지 않고 `regions.ldong_cd` 로 집계 |

**상세(`detailCommon2`)에서 오는 것**

| 응답 필드 | 컬럼 | 비고 |
|---|---|---|
| `overview` | `summary` | HTML 태그를 벗기고 **첫 문장만** |
| `tel` | `phone` | 아래 `infocenter*` 가 비었을 때만 |

**상세(`detailIntro2`)에서 오는 것** — 콘텐츠타입마다 필드 이름이 다릅니다.

| 음식점(39) | 관광지(12) | 문화시설(14) | 컬럼 |
|---|---|---|---|
| `opentimefood` | `usetime` | `usetimeculture` | `open_hours` |
| `infocenterfood` | `infocenter` | `infocenterculture` | `phone` |

**API 가 주지 않아 우리가 정하는 값**

| 컬럼 | 값 | 이유 |
|---|---|---|
| `source_rating` | `null` | TourAPI 는 평점을 주지 않는다. `0` 으로 두면 '평점 없음'과 '0점'이 구분되지 않아 전 장소가 ★ 0.0 으로 보인다 |
| `price_level` | `2` 고정 | 근거가 될 값이 응답에 없다 |
| `tags` | 빈 배열 | 취향 태그와 맞출 신뢰할 원천이 없어 추측해 채우지 않는다 |
| `region_source` | 판정 경로 | `tour`/`addr`/`geo`/`manual`/`unresolved` |
| `region_note` | 미판정 사유 | 관리자가 다시 조사하지 않고 판단하도록 |

### 2-4. 응답이 들어가지 않는 테이블

`profiles`(닉네임·취향 태그) · `trips`(여행) · `trip_items`(타임라인·방문 리뷰) ·
`reservations`(예약)는 전부 **사용자가 앱에서 만드는 데이터**입니다. 수집 배치는
이 네 테이블을 읽지도 쓰지도 않습니다.

다만 `trip_items.place_id` 와 `reservations.place_id` 가 `places` 를
`on delete cascade` 로 참조하므로, **장소를 지우면 사용자 데이터가 함께 지워집니다.**
수집이 이 테이블들에 간접적으로 닿는 유일한 경로이고, 4단계의 주의가 그것입니다.

## 3. 적재 SQL 생성 — `raw/` → `seed.sql`

```bash
node load.mjs --demo            # supabase/seed.sql + src/lib/seed.ts 생성
node load.mjs --dry             # 파일을 쓰지 않고 리포트만
```

**네트워크를 쓰지 않습니다.** 판정 로직을 고쳤을 때 이 단계만 다시 돌리면 됩니다.

여기서 하는 일은 셋입니다.

**지역 판정** — 1순위 응답의 `sigunguCode`, 2순위 주소에서 시군구명 매칭,
3순위 좌표 경계(아직 쓰지 않음), 실패하면 미판정 코드 `-1` 로 격리하고 사유를
`region_note` 에 남깁니다. 실측으로 99.81%가 1순위로 해결됩니다.

**좌표 검증** — TourAPI 원본에 좌표가 통째로 잘못된 행이 섞여 있습니다(전국 30건이
전부 `19.694, 117.993`, 필리핀 앞바다). 한국 범위를 벗어나면 미판정으로 격리합니다.
그대로 두면 지도에 엉뚱한 곳에 찍히고 동선 계산이 망가집니다.

**카테고리 매핑** — 밥집·카페·술집·명소로 접습니다. 술집은 `cat3` 에 코드가 없고
`lclsSystm2` 의 `FD04` 로만 잡히는데 전국 3건뿐입니다.

리포트에서 반드시 볼 것은 **판정 경로별 비율**과 **적재하지 않은 시군구 목록**
입니다. 후자는 대개 폐지된 행정구역(진해시·마산시·남제주군 등)이 TourAPI 코드표에
남아 있는 경우로, 장소가 0곳이라 넣지 않습니다.

`--demo` 를 붙이면 데모 모드용 `src/lib/seed.ts` 도 함께 만듭니다. 지역은 전량,
장소는 몇 개 시군구만 골라 담습니다.

## 4. DB 적용 — `seed.sql` → Supabase

```bash
npx supabase db push --linked --include-seed
```

**`--include-seed` 가 없으면 마이그레이션만 올라가고 장소는 들어가지 않습니다.**
`db push` 의 기본 동작이 그렇습니다.

실행하면 확인을 묻습니다. 적용되지 않은 마이그레이션 목록이 뜨는데, **예상한
파일만 떠야 정상**입니다. 이전 것들이 같이 뜨면 원격 이력이 로컬과 다르다는
뜻이니 멈추고 확인하세요.

seed 가 3.6MB 라 몇 분 걸릴 수 있습니다. 출력이 멈춘 것처럼 보여도 정상입니다.

### 주의

스키마를 교체하는 마이그레이션은 **`places`·`regions`·`region_groups` 를 drop 하고
`trips`·`trip_items`·`reservations` 를 비웁니다.** 되돌릴 수 없습니다. 특히
`trip_items.note`·`rating`(사용자가 쓴 방문 리뷰)은 외부 출처가 없어 다시 만들
수 없습니다.

`places` 를 참조하는 두 컬럼이 `on delete cascade` 라, **장소를 지우면 사용자의
타임라인과 예약이 조용히 함께 지워집니다.** 재수집이 고아 장소를 정리할 때도
같은 일이 일어날 수 있으므로, 정리 로직은 반드시 "이번 응답에 없고
`trip_items`·`reservations` 어디에서도 참조되지 않는 행"만 골라야 합니다.

## 5. 확인

### 5-1. 화면

**비로그인 상태로 지도 탭**을 여는 게 가장 빠릅니다. 지역 드롭다운에 시/도가
뜨고 구를 고르면 장소가 나오면, RLS 공개 읽기 정책까지 제대로 재생성된 것입니다.

- 별점이 없는 장소에 `★ 0.0` 이 보이면 안 됩니다
- 소개·영업시간이 빈 장소에 빈 칸이나 빈 제목이 남으면 안 됩니다
- 드롭다운에 '미판정' 이 보이면 안 됩니다

### 5-2. 쿼리

```sql
-- 판정 경로별 분포. unresolved 가 급증했다면 수집·판정에 문제가 생긴 것이다
select region_source, count(*) from public.places group by 1 order by 2 desc;

-- 수동 처리 대기열
select id, name, address, region_note
from public.places
where tour_sigungu_code < 0
order by name;

-- 상세가 아직 안 채워진 비율
select count(*) filter (where summary = '') * 100.0 / count(*) as 소개_빈_비율
from public.places;
```

### 5-3. 미판정 처리

대기열의 장소는 주소와 좌표가 그대로 남아 있으므로, 올바른 코드 쌍을 넣으면
그 자리에서 서비스에 등장합니다.

```sql
update public.places
set tour_area_code = 1, tour_sigungu_code = 5
where id = '<contentid>';
```

`region_source` 는 건드리지 않아도 됩니다 — 트리거가 자동으로 `'manual'` 로
바꾸고 `region_note` 를 비웁니다. 그리고 `'manual'` 인 행은 **재적재가 지역을
덮어쓰지 않습니다.**

## 6. 자주 걸리는 곳

| 증상 | 원인과 조치 |
|---|---|
| `ERR_NAME_NOT_RESOLVED` (브라우저) | Supabase 프로젝트가 **Paused**. 대시보드에서 Restore. 무료 플랜은 일정 기간 활동이 없으면 재운다 |
| `project is paused` (`link` 실행 시) | 위와 같음 |
| `Cannot find project ref` | `supabase/.temp` 가 없다. `npx supabase link --project-ref <ref>` 를 먼저 |
| `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` | `.key` 를 반대쪽(Encoding ↔ Decoding) 키로 바꿔 본다. 발급 직후면 활성화를 잠시 기다린다 |
| 수집이 매번 같은 곳에서 멈춤 | 일일 한도. 정상이다. 다음 날 다시 돌리면 이어진다 |
| 마이그레이션만 적용되고 장소가 없음 | `--include-seed` 를 빠뜨렸다 |
| `No matching Supabase CLI binary package found for darwin-arm64` | 다른 OS 에서 `npm install` 이 돌아 플랫폼 바이너리가 바뀌었다. `rm -rf node_modules && npm install` |
| 지도에 장소가 엉뚱한 곳에 찍힘 | 좌표 검증을 건너뛴 적재. `load.mjs` 를 다시 돌려 재적재 |
