## 1. 배경

외부 검토 문서가 스키마와 접근 계층을 훑고 리스크 세 갈래와 확장 제안 두 갈래를
냈습니다. 사실관계는 대체로 정확했고 — 인덱스 누락, 제약 부재, enum 잔여값은 실제로
그대로였습니다 — 결론 하나가 이미 내린 결정과 충돌합니다.

검토자가 스키마만 보고 판단했기 때문입니다. "공유하려면 RLS 를 열어야 한다"는
스키마만 놓고 보면 자연스러운 추론이지만, **왜 그렇게 하지 않기로 했는지는 다른
문서에 있었습니다.** 이 문서는 그 간극을 메워 기록으로 남깁니다.

## 2. 적용 — 외래키 인덱스 세 개 **[적용]**

현재 인덱스 여섯 개를 전부 확인했고, 아래 셋이 없는 것이 맞습니다.

```
trip_items   (trip_id, sort_order)      ← place_id 없음
reservations (user_id, reserved_at)     ← place_id · trip_item_id 없음
```

`trip_items.place_id` 와 `reservations.place_id` 는 `places` 를 **`on delete cascade`**
로 참조합니다. 인덱스가 없으면 `places` 에서 한 행을 지울 때마다 Postgres 가 자식
테이블을 통째로 훑어 참조를 찾습니다. 재수집이 고아 장소를 정리하는 경로에서 바로
걸리는 비용입니다.

`reservations.trip_item_id` 는 `on delete set null` 이라 같은 이유로 필요합니다.

## 3. 적용 — 예약금 음수 방지 **[적용]**

`reservations.deposit` 이 `integer not null default 0` 인데 음수를 막는 제약이
없습니다. 결제 연동이 아직 없어 지금은 앱이 음수를 넣지 않지만, 제약이 없는 채로
연동을 붙이면 잘못된 값이 조용히 쌓입니다.

## 4. 적용 — 동행인 값 검증 **[적용]**

`trips.companions` 가 `text[]` 자유 입력이라 `'solo'`·`'couple'`·`'friends'`·
`'family'`·`'pet'` 외의 문자열이 들어갈 수 있습니다. 들어가면 화면에서 라벨을 찾지
못해 빈 칸이 되는데, **오류 없이 조용히 지나갑니다.**

배열 포함 검사(`<@`)는 싸고, 빈 배열도 통과합니다. 동행인 종류를 나중에 늘릴 때
마이그레이션이 한 건 필요하지만, enum 을 쓰는 것과 같은 성격의 비용입니다.

## 5. 보류 — 장소명 검색 인덱스 **[보류]**

검토 문서는 `ilike('name', '%키워드%')` 가 인덱스를 못 타니 `pg_trgm` 확장과 GIN
삼중자 인덱스를 넣자고 제안합니다. 동작 설명은 맞습니다.

**그런데 그 필터를 넘기는 화면이 하나도 없습니다.** `PlaceFilter.keyword` 는
`db.ts` 에만 있고 `src/` 어디에서도 값을 채우지 않습니다 — 지금은 죽은 코드라
Full Table Scan 이 일어날 일이 없습니다.

확장 모듈과 GIN 인덱스는 공짜가 아닙니다. **장소 검색 UI 를 실제로 만들 때 함께
넣습니다.** 그때 이 절을 근거로 쓰면 됩니다.

## 6. 보류 — `trip_item_status` 의 `'waiting'` 잔여값 **[보류]**

웨이팅 기능은 `20260825040000_drop_waiting_feature.sql` 로 제거됐는데 enum 에는
값이 남아 있습니다. 지적은 맞습니다.

다만 **해를 끼치지 않습니다.** 코드가 그 값을 쓰지 않고, 쓰이지 않는 enum 값은
저장 공간이나 성능에 영향이 없습니다. 반면 제거하려면 타입을 새로 만들고 컬럼을
재캐스팅해야 해서, 얻는 것에 비해 건드릴 면적이 큽니다.

`trip_items` 를 어차피 손대는 다음 스키마 변경이 생기면 그때 묶어서 정리합니다.

## 7. 기각 — `trips.is_public` 과 RLS 개방 **[기각]**

검토 문서 5.1 은 플랜 공유를 위해 `trips` 에 `is_public` 을 추가하고 `trips` ·
`trip_items` 의 SELECT 정책을 `or is_public = true` 로 여는 안을 제시합니다.

**[플랜 공유 intent](../2026-09-20-플랜-공유/intent.md) 의 D1 이 이미 기각한
방식입니다.**

> `trips` 행에 `is_public` 을 켜서 RLS 를 여는 방식은 만들기는 쉽지만 받아들일 수
> 없습니다. `trips` 에는 `trip_date`(내가 언제 어디 있었는지)·`companions`(누구와
> 갔는지)가 있고, `trip_items` 에는 `note`·`rating`(개인 리뷰)과 `status`가
> 있습니다. "이 여행 공개"를 켜는 순간 이 전부가 따라 나갑니다.

검토 문서가 제안한 정책을 그대로 적용하면 **공개 플랜을 연 사람이 작성자의 방문
리뷰와 별점, 정확한 여행 날짜까지 보게 됩니다.** 사용자가 공개하려는 건 동선이지
일기가 아닙니다.

합의된 설계는 공개 시점에 `shared_plans` · `shared_plan_items` 로 **필요한 것만
복사**하는 스냅샷 방식입니다. 담기가 "복제"이지 "참조"가 아닌 이유(D3), 담은 수
카운트가 `security definer` 함수여야 하는 이유(D4)도 같은 문서에 있습니다.

검토 문서의 "가져오기 시 `rating`·`note`·`status` 를 초기화한다"는 지적은 맞고,
이미 D3 에 그렇게 적혀 있습니다.

## 8. 검토가 놓친 것 — `places` 삭제의 연쇄 **[기록]**

리스크 항목에 없지만 이게 더 큽니다. `trip_items.place_id` 와
`reservations.place_id` 가 `on delete cascade` 라, **`places` 에서 행을 지우면
사용자의 타임라인과 예약이 조용히 함께 지워집니다.**

이번 스키마 교체에서 실제로 그 경로로 모든 여행 데이터가 사라졌습니다(테스트
단계라 합의된 것이었습니다). 앞으로도 재수집이 "이번 응답에 없는 장소"를 정리할 때
같은 일이 일어날 수 있습니다.

재수집 쪽 문서 8번이 이미 **"`trip_items`·`reservations` 어디에서도 참조되지 않는
행만 골라 지운다"** 고 정해뒀습니다. 그 규칙이 지켜지는지가 이 위험을 막는 유일한
장치이므로, 적재 스크립트에 정리 로직을 넣을 때 반드시 확인해야 합니다.

`region_source = 'manual'` 인 행을 보호하는 것과 같은 성격의 규칙입니다.

## 9. 사용자 평점 집계 **[기록]**

검토 문서 5.2 의 지적(실사용자 `rating` 을 `places` 로 환산)은 타당하고, 재수집
문서 6번에서 이미 **별도 과제로 뺀** 사안입니다. 이유도 거기 적혀 있습니다 —
`trip_items` 가 RLS 로 본인 행만 보이므로 단순한 뷰로 집계하면 사용자마다 자기
리뷰만 평균한 값이 나옵니다. `security definer` 함수나 리뷰 테이블 분리가 필요하고,
후자는 플랜 공유와 맞물립니다.

여기서 새로 정할 것은 없습니다.

## 10. 수용 기준

- [ ] `places` 에서 장소 하나를 지울 때 `trip_items`·`reservations` 를 전체 스캔하지 않는다
- [ ] `reservations` 에 음수 `deposit` 을 넣으려는 시도가 제약에서 막힌다
- [ ] `trips.companions` 에 정의되지 않은 값을 넣으려는 시도가 제약에서 막힌다
- [ ] 빈 `companions` 배열은 그대로 통과한다
- [ ] 기존 데이터가 새 제약을 위반하지 않아 마이그레이션이 통과한다
- [ ] `npx tsc --noEmit` · `npm run build` 통과 (스키마만 바뀌므로 코드 영향은 없어야 한다)
