## 2. 무엇을 왜

### 2.1 홈 '하루에 다녀올 만한 곳'

이전 홈은 '인기'라는 이름과 달리 순위가 없었고, 장소 전체를 받으려다 API 상한
1,000행에 잘려 이름순 앞쪽 다섯 지역에서만 나왔습니다. 자세한 흐름 · 결정 ❶~❺ ·
규칙 표는 [README-플로챠트.md](../../README-플로챠트.md) 에 있습니다. 요약하면:

- 기준점은 현재 위치, 거부 · 미지원 · 5초 무응답이면 서울 강남구 중심.
- DB 함수 `home_picks()` 가 고른다. 종류마다 반경 120km 안 리뷰 있는 곳을 평균
  순으로 먼저, 나머지는 가까운 순. 명소 3 · 밥집 1 · 카페 1.
- 처음 설계는 '반경 안 무작위'였는데 가까운 순으로 바꿨고, 가까운 순만으로는 반경
  수백 m 의 식당 · 카페만 나와 종류별 자리를 뒀습니다.
- 카드의 이동 시간: 걸어서 15분 안이면 '도보', 아니면 '차로'(처음 10km 30km/h,
  나머지 80km/h). 전부 80km/h 로 나누면 '차로 약 1분'이 됐습니다.

### 2.2 장소 별점

- `places.rating_avg` · `rating_count` — 개인 리뷰(`trip_items.rating`)를 **사람당
  가장 최근 한 표**로 모은 평균. 리뷰가 바뀔 때 트리거가 그 장소만 다시 계산합니다.
  여행 삭제 · 탈퇴 cascade 도 트리거가 받습니다.
- 트리거 함수는 `security definer` — 리뷰 쓴 사람의 권한이면 RLS 때문에 자기 리뷰만으로
  평균을 내고(오류 없이 틀린 값), `places` 쓰기도 관리자만이라서입니다.
- 화면 ★ 는 리뷰 3건 이상일 때만(`shownRating()`). 1건이면 평균이 곧 그 사람의 별점이라
  숨기되, 순서에는 반영합니다.

### 2.3 추천 장소 순위

- 별점 항 `ratingScore()` — 리뷰가 적을수록 3점 쪽으로 당긴 평균(가상 보통 리뷰 2건),
  별 1개당 2점. 5점 1건 +1.3 · 3건 +2.4 · 10건 +3.3.
- 점수가 같으면 무작위 — 목록이 이름순으로 와서 동점이 가나다순 앞쪽으로만 채워졌습니다.
- 한 종류는 목록의 절반(8곳 중 4곳)까지 — 시간대 · 날씨 가산이 종류 단위라 맑은 저녁에
  명소 8곳처럼 쏠렸습니다.
- 저녁(17:00~20:59) 밥집 +4 — 점심 가산만 있어 맑은 저녁 추천에 밥집이 빠졌습니다.

### 2.4 취향 태그

`places.tags` 가 전부 비어 있어 회원 취향 태그(온보딩에서 고름)가 추천에 전혀 쓰이지
않았습니다. TourAPI 응답의 정해진 칸 · 메뉴 글자에서 **확실히 나오는 다섯만** 채웁니다
(`load.mjs` 의 `tagsOf()`).

| 태그 | 근거 | 장소 수 |
|---|---|---|
| 주차가능 | parking · parkingfood · parkingculture 가 '가능' · '있음'('불가' 제외) | 6,323 |
| 카페 | 장소 분류 | 1,849 |
| 심야영업 | 명소 제외, 자정 이후 마감(24:00 · 00~05시) · 24시간 · 익일 — 처음엔 23시 마감부터(460곳)였다가 좁힘 | 240 |
| 디저트 | 메뉴에 디저트 · 케이크 · 베이커리 · 젤라토 등 | 282 |
| 오마카세 | 메뉴에 '오마카세' | 19 |

**취향 태그는 이 다섯만 남겼습니다.** 처음에는 근거 없는 태그도 온보딩 선택지에 남겼는데,
골라도 추천에 반영되지 않는 선택지라 정리했습니다.

- 반려견 관련(`20261008070000_drop_pet`) — 취향 태그 '반려견 동반'과 여행 · 코스의 동행인
  'pet'을 화면 · 타입 · DB 제약에서 빼고 저장값도 정리. 반려동물 정보는 TourAPI 별도 서비스라
  받지 않습니다.
- 나머지 여섯(`20261008080000_drop_unused_taste_tags`) — 비건 · 노포 · 뷰맛집(소개 글 추정뿐,
  오탐) · 가성비 · 혼밥 · 로컬맛집(근거 값 없음). 선택지와 저장값에서 지움.
상세를 아직 받지 못한 장소(약 49%)는 '카페' 말고는 비어 있고, 수집이 진행되면 채워집니다.

### 2.5 1,000행 상한

API 는 한 번에 최대 1,000행만 주고 넘쳐도 오류 없이 자릅니다. 지도 · 추천 장소 · 방문
조건에서 '시/도 전체'가 1,000곳을 넘는 일곱 곳(경기 3,357곳 최대)이 이름순 앞쪽만
받았습니다. `places.list()` 가 첫 쪽에서 개수를 받고 나머지 쪽을 한꺼번에 받습니다.
지도는 수천 곳을 이름표 마커로 그리면 무거워 '시/도 전체'일 때 점으로 그립니다.

## 4. 운영 반영 순서

프런트엔드는 push 하면 Vercel 이 배포합니다. 새 화면은 옛 DB 에서도 깨지지 않게 짰고
(홈 '하루에 다녀올 만한 곳'만 비어 보임), 옛 화면은 새 DB 에서 예약을 읽다가 실패하므로
**push → DB** 순서가 맞습니다.

1. `git push origin main`
2. (선택) 예약 백업 — SQL 편집기에서 `select * from reservations;` 결과를 CSV 로
3. `npx supabase migration list --linked` — Remote 가 빈 줄이 들어갈 마이그레이션
4. `npx supabase db push --linked`
5. SQL 편집기: `delete from supabase_migrations.seed_files;`
6. `npx supabase db push --linked --include-seed` — **4 다음에.** 새 시드에는 지운 두 칸이
   없다. 시드는 upsert 라 리뷰 · 별점 집계는 그대로 남는다.
7. [점검.sql](점검.sql) 의 ①~⑤ 를 **하나씩** 실행 — SQL 편집기는 여러 문장을 한꺼번에
   돌리면 마지막 결과만 보여 준다.

| 점검 | 기대값 |
|---|---|
| ① 지운 것 · 새로 생긴 것 | `t` · `t` · `t` · `{planned,visited}` |
| ② 별점 집계 = 실제 리뷰 | 어긋난_장소 `0` |
| ③ 홈 함수를 anon 으로 | 5행 — 명소 3 · 밥집 1 · 카페 1 |
| ④ 영업시간 | dash_dash `1`(원문 오타) · 여러줄 약 3,000 |
| ⑤ 반려견 · 옛 취향 태그 정리 | `0` · `0` · `0` |

## 5. 검증한 방법

- 마이그레이션 전체(34개)를 빈 DB 에 재생한 결과와 `schema.sql` 을 `pg_dump` 로 비교 —
  diff 0줄. 함수 본문 안 주석도 DB 에 저장되므로 비교에 걸린다(한 번 걸려서 되돌림).
- 별점 트리거: 다른 사람 리뷰 포함 · 사람당 최근 한 표 · 여행 날짜 변경 · cascade 삭제 ·
  일반 사용자의 `places` 수정 차단.
- 1,000행: 실제 PostgREST 를 상한 1,000 · 700 으로 띄워 여섯 조건 — 개수 일치 · 중복 없음.
- 시드 재생성: 이전/이후 시드를 임시 DB 두 벌에 넣고 비교 — 의도한 칸 외 변화 0행.
- 데이터 삭제 마이그레이션: 칸 · 테이블 · 값이 있는 DB 에 적용해 확인.
- 화면: 데모 모드 빌드를 Playwright 로 띄워 스크린샷.
