# 재수집 배치

이 폴더의 `collect.mjs` 는 [intent.md](intent.md) 8번에서 정한 **수집 단계**를
수행하는 1회성 스크립트입니다. 적재(마이그레이션)는 아직 만들지 않았습니다 —
열린 질문 Q4(법정동코드 컬럼)가 DDL 에 걸려 있어 스키마가 확정된 뒤에 씁니다.

## 하는 일과 하지 않는 일

`areaCode2` 로 시/도·시군구 코드표를 받고, 시군구별로 `areaBasedList2`(목록)를 돌린
뒤, 장소별로 `detailCommon2`(소개) + `detailIntro2`(영업시간·전화)까지 받습니다.
**원본 응답을 그대로** `raw/` 에 쌓고 마지막에 리포트를 출력합니다.

좌표 역판정, 구 확정, 미판정(`-1`) 처리, 카테고리 매핑, DB 적재는 **하지 않습니다.**
판정 로직은 나중에 고칠 수 있고, 그때 API 를 다시 때리지 않으려면 원본이 남아 있어야
합니다.

## 실행

```bash
node collect.mjs                # 전국, 목록 + 상세
node collect.mjs --area 1       # 특정 시/도만 (areaCode)
node collect.mjs --skip-detail  # 목록만
node collect.mjs --detail-only  # 이미 받은 목록으로 상세만
node collect.mjs --report-only  # 이미 받은 파일로 리포트만 다시 출력
node collect.mjs --backfill-mt  # 예전에 받은 상세에 modifiedtime 채우기 (호출 0회)
```

키는 이 폴더의 **`.key`** 에서 읽습니다. 파일을 열어 주석 아래에 서비스 키를 한 줄로
붙여 넣으세요. `.key` 는 `.gitignore` 에 있어 커밋되지 않고, `.env` 에도 넣지 않습니다.
비어 있으면 실행할 때 입력받습니다 — 며칠에 걸쳐 여러 번 이어서 실행해야 하므로
파일에 두는 편이 편합니다.

**첫 실행은 `--area 1` 로 서울만 돌려 보세요.** 응답 모양과 키 인코딩을 몇 십 호출
안에 확인할 수 있고, 잘못됐으면 `raw/` 를 비우고 다시 시작하면 됩니다.

**중단해도 안전합니다.** 목록은 시군구 × 콘텐츠타입 단위로 파일을 쓰고 이미 있으면
건너뜁니다. 상세는 같은 파일 단위 안에서 `contentid` 별로 기록하고 **한 곳을 받을 때마다
저장**하므로, 어느 지점에서 죽어도 그때까지 받은 건 남습니다. 일일 호출 한도에 걸리면
다음 날 그냥 다시 실행하면 이어서 받습니다.

## 열흘에 걸쳐 전국을 받기

일일 호출 한도에 걸리면 `collect.mjs` 는 그 자리에서 멈춥니다. 이미 받은 것은
건너뛰므로 다음 날 다시 실행하면 이어집니다. 그 "다음 날 다시"를 자동으로 해주는
것이 `run-daily.sh` 입니다.

```bash
./run-daily.sh            # 한 번 이어서 받기 (로그는 raw/logs/ 에)
./run-daily.sh --status   # 전체 진행률만 확인
```

매일 자동으로 돌리려면 같은 폴더의 launchd 설정을 올립니다.

```bash
cp com.danyoh.oneday-trip.collect.plist ~/Library/LaunchAgents/
launchctl load ~/Library/LaunchAgents/com.danyoh.oneday-trip.collect.plist
```

매일 00:10 에 실행되고, 그 시각에 맥북이 잠들어 있었다면 깨어날 때 실행됩니다
(cron 은 이 경우 그날을 건너뜁니다 — 열흘짜리 작업에서 차이가 큽니다). 끝난 뒤
해제는 `launchctl unload` 입니다.

무인 실행이므로 **`.key` 에 키가 들어 있어야 합니다.** 대화형 입력은 이때 쓸 수
없습니다.

진행 상황은 `raw/logs/summary.txt` 에 실행마다 한 줄씩 쌓입니다.

## 재수집은 바뀐 것만 받는다

상세 항목마다 수집 시점의 목록 `modifiedtime` 을 `mt` 로 같이 저장합니다. 그래서
다시 실행하면 **새로 생겼거나 `modifiedtime` 이 바뀐 곳의 상세만** 받습니다. 첫
수집 중에는 전부 새 항목이라 동작이 같고, 한 바퀴 돈 뒤부터 호출이 한 자릿수
퍼센트로 줄어듭니다.

`mt` 를 도입하기 전에 받아 둔 상세는 `--backfill-mt` 로 채웠습니다 — 이미 받은
상세는 그때 목록과 같은 시점의 것이라 다시 받을 이유가 없어서, 호출 0회로 끝납니다.

## 얼마나 걸리나

**실측(2026-09-22): 전국 목록은 234개 시군구 15,518곳입니다.** 호출은 코드표 18 +
목록 약 700 + 상세 약 31,000 = **약 31,700회**이고, 상세가 98%를 차지합니다.

**실측: 일일 한도는 2,000 호출로 보입니다** — 이틀 연속 장소 1,000곳(상세 2,000
호출)씩 받고 멈췄습니다. 이 속도면 남은 분량에 2주쯤 걸립니다. 재개되니 며칠에 걸쳐 돌아가는 것
자체는 문제가 아니지만, 이 규모면 운영계정 전환이 사실상 필요합니다 — 키를 새로
받는 게 아니라 같은 키의 한도를 올리는 절차입니다.

## 첫 실행에서 확인할 것

리포트가 intent.md 12번의 열린 질문들을 닫아 줍니다.

- **시/도 이름 원문** — `'서울'` 인지 `'서울특별시'` 인지, 광주·전남이 통합돼
  내려오는지 (Q2)
- **시군구별 장소 수 분포** — 구 단위로 플랜이 성립하는 지역이 몇 개인지 (Q5)
- **`areacode`·`sigungucode`·좌표가 빈 건수** — 미판정으로 남을 규모, 수동 처리
  화면이 필요한지 (Q7)
- **콘텐츠타입별 건수** — 술집을 다른 소스로 보충해야 하는지 (Q6)
- **상세 충족 비율** — `overview`·영업시간·전화가 실제로 몇 %나 채워지는지

## 알아두기

- 공공데이터포털 키는 Encoding / Decoding 두 가지로 발급됩니다. 스크립트가 `%` 포함
  여부로 갈라 처리하지만, `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` 가 나면 다른 쪽 키로
  바꿔 보세요 — 첫 실행 실패의 가장 흔한 원인입니다.
- TourAPI 가 `overview`·영업시간·전화를 **주지 않는 장소가 섞여 있습니다.** 상세를
  받아도 빈 값이 남으니, 리포트의 충족 비율을 보고 화면에서 그 영역을 숨기는 처리를
  해야 합니다(intent.md 8·9번).
- `detailIntro2` 는 콘텐츠타입마다 필드 이름이 다릅니다(음식점은 `opentimefood`,
  관광지는 `usetime`, 문화시설은 `usetimeculture`). 스크립트는 원본을 그대로 저장하고,
  이름을 맞추는 일은 적재 단계에서 합니다.
- `.key` 와 `raw/` 는 커밋하지 않습니다(`.gitignore`). 언제든 다시 받을 수 있고 수천 개 파일입니다.
  `raw/report.json` 은 결정의 근거라 남깁니다.
- 콘텐츠타입은 음식점(39)·관광지(12)·문화시설(14) 셋입니다. 앱 카테고리(밥집·카페·
  술집·명소)로 접는 일은 적재 단계에서 `cat1`/`cat2`/`cat3` 을 보고 합니다.
