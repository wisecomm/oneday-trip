## 1. 배경

### 지금 구조

지역은 상위(시/도) · 하위(구/시) 2단이고, **키가 이름 문자열**입니다.

```
region_groups.name = '서울'          (PK, text)
        ↑ group_name
regions.name       = '서울 성동구'    (PK, text)
        ↑ region
places.region      = '서울 성동구'
```

`regions.name` 에 `'서울 '` 접두어를 붙이는 건 **강서구가 서울과 부산에 둘 다 있고**,
중구·서구·동구·남구·북구가 여러 광역시에 중복되기 때문입니다. `'서구'` 만 쓰면
`'강서구'` 안에 부분 문자열로 들어가 뒤섞이는 문제도 있습니다. 즉 이름을 키로 쓴
대가로 접두어 규칙이라는 우회를 하나 지고 있습니다.

`trips.destination` 은 더 불편합니다. `regions.name`(리프) 또는
`region_groups.name`('전체' 선택 시) **둘 중 하나**를 담는데, 두 테이블 중 하나를
가리키는 FK 는 표현할 수 없어 **제약 없이** 두고 있습니다(schema.sql 주석). 오타나
지역 개편으로 값이 끊어져도 DB 는 아무 말을 하지 않고, 화면에서 목적지가 조용히
빈칸이 됩니다.

## 3. 결정 — 복합키로 간다 **[확정]**

`(area_code, sigungu_code)` 복합키를 씁니다. 대리키(`region_id` 하나)를 두고
복합 unique 를 거는 방법도 있지만, 테이블이 몇 개 안 되고 대리키를 두면 "코드로
저장한다"는 목적이 한 겹 가려집니다. `area_code = 1 and sigungu_code = 5` 가
조인 한 단계를 더 타는 것보다 읽기 쉽습니다.

### 컬럼 이름에 출처를 드러낸다 **[확정]**

**TourAPI 코드는 한국관광공사 자체 코드이지 행정표준코드(법정동코드)가 아닙니다.**
서울이 `1`, 부산이 `6` 인 건 관광공사 내부 번호이고 행정안전부 체계와 다른 숫자입니다.
지금은 장소 출처가 TourAPI 하나라 문제가 없지만, 나중에 카카오 로컬이나 다른
공공데이터를 섞으면 그쪽 코드와 매칭되지 않습니다.

그래서 컬럼 이름을 `area_code` 가 아니라 **`tour_area_code` · `tour_sigungu_code`**
로 둡니다. 이 숫자가 무엇인지 스키마만 보고 알 수 있어야, 나중에 법정동코드를
추가할 때 섞이지 않습니다.

**법정동코드는 이번에 같이 넣습니다 [확정].**

처음에는 "채울 출처가 없어 100% null 인 컬럼이 생긴다"는 이유로 미루기로 했는데,
서울 수집 결과가 그 전제를 뒤집었습니다. `areaBasedList2` 응답이 **`lDongRegnCd` ·
`lDongSignguCd` 를 함께 실어 보냅니다** — 강남구는 `11` + `680`, 정확히 행정표준코드
11680 입니다. 서울 1,539건 **전부(100%)** 에 들어 있었습니다.

그러면 판단이 반대가 됩니다. 지금 넣으면 수집 단계에서 공짜로 채워지고, 안 넣으면
나중에 필요해질 때 **전량 재수집**을 해야 채워집니다. 카카오 로컬 같은 다른 소스는
TourAPI 코드로는 맞출 수 없지만 법정동코드로는 맞습니다.

넣는 자리는 `places` 가 아니라 **`regions`** 입니다. 법정동코드는 장소가 아니라
시군구의 속성이라 장소마다 들고 있으면 중복입니다. `areaCode2` 는 이 값을 주지 않으므로,
적재할 때 그 시군구에 속한 장소들이 보내온 `lDong*` 값으로 채우고 서로 어긋나는 게
있으면 리포트에 남깁니다.

### `sigungu_code` 는 단독으로 유일하지 않다

`sigungu_code = 1` 은 서울에서와 부산에서 서로 다른 구를 가리킵니다. 반드시
`area_code` 와 **쌍으로만** 의미가 있습니다 — 복합키를 쓰는 직접적인 이유입니다.

## 4. 바뀌는 스키마

복합키 골격은 **[확정]**. 아래 표시된 자리만 열려 있습니다.

### `region_groups`

| 컬럼 | | 비고 |
|---|---|---|
| `tour_area_code` | smallint **PK** | TourAPI `areaCode` |
| `name` | text not null **unique** | `'서울'` |
| `lat`, `lng` | | 지도 초기 중심 — 유지 |
| `sort_order` | smallint | 유지 |

### `regions`

| 컬럼 | | 비고 |
|---|---|---|
| `tour_area_code` | smallint | FK → `region_groups` |
| `tour_sigungu_code` | smallint | |
| **PK** | `(tour_area_code, tour_sigungu_code)` | |
| `name` | text not null | **`'성동구'` — 접두어 없음** |
| unique | `(tour_area_code, name)` | 같은 시/도 안에서만 이름이 유일하면 됨 |
| `ldong_cd` | text(5), nullable | 행정표준코드(법정동) `lDongRegnCd` + `lDongSignguCd`. 다른 데이터 소스와 맞추는 열쇠 |
| `lat`, `lng`, `sort_order` | | 유지 |

접두어 규칙이 사라지는 게 이 변경의 눈에 보이는 이득입니다. 서울 강서구와 부산
강서구가 이름은 같아도 코드가 달라 충돌하지 않습니다.

여기에 **미판정 행**이 함께 들어갑니다 — 시/도마다 `(N, -1)` 하나씩과 시/도조차
모를 때를 위한 `(-1, -1)` 하나입니다. 자세한 건 5번을 보세요.

### `places`

`region` 컬럼을 빼고 `tour_area_code` · `tour_sigungu_code` 를 넣어 `regions` 에
복합 FK 를 겁니다. `id` 는 지금처럼 TourAPI `contentid` 를 그대로 씁니다.
인덱스는 `(tour_area_code, tour_sigungu_code, category)` 로 다시 만듭니다.

`tour_sigungu_code` 는 **항상 NOT NULL** 입니다 **[확정]**. 세종처럼 구를 모르는
경우는 null 이 아니라 미판정 코드 `-1` 을 넣습니다 — 미판정 장치가 있으니 null 을
허용할 이유가 없습니다.

**`rating` 을 `source_rating` 으로 바꾸고 nullable 로 둡니다 [확정].** 외부에서 받아온
값과 우리가 만든 값을 한 필드에 섞지 않기 위한 것이고, 이유는 6번에 따로 적습니다.

**`source_modified_at`** 도 함께 둡니다 **[확정]** — TourAPI 목록의 `modifiedtime`
입니다. 재수집 때 "바뀐 것만 상세를 다시 받는" 판단의 근거이고, 15,518건 100%에
채워져 있음을 실측으로 확인했습니다(8번).

여기에 판정 이력을 담는 컬럼 두 개를 더 둡니다 **[확정]**. 자세한 쓰임은 5번에 있습니다.

| 컬럼 | 값 | 용도 |
|---|---|---|
| `region_source` | `'tour'` · `'addr'` · `'geo'` · `'manual'` · `'unresolved'` | 지역을 **어느 순위로** 판정했는지(5번). 재수집이 사람이 고친 값을 덮어쓰지 않게 하는 근거 |
| `region_note` | text, nullable | 미판정 사유 한 줄. 관리자가 다시 조사하지 않고 바로 판단하도록 |

### `trips` — 여기가 제일 크게 좋아진다

`destination` text 를 빼고 `tour_area_code`(not null) · `tour_sigungu_code`(nullable)
두 컬럼으로 바꿉니다.

**`sigungu_code` 가 `null` 이면 '시/도 전체'** 입니다. 지금 문자열 하나에 두 층위를
섞어 담던 걸 두 컬럼이 자연스럽게 표현합니다.

`null` 과 `-1` 의 의미가 갈리는 지점이라 헷갈리지 않게 적어 둡니다 **[확정]**.

| 값 | 뜻 |
|---|---|
| `null` | 사용자가 '시/도 전체'를 **의도적으로 선택** |
| `-1` | 구를 **모름** (미판정) — `places` 에만 쓰이고 `trips` 에는 나타나지 않음 |

그리고 Postgres 의 복합 FK 는 기본이 `MATCH SIMPLE` 이라 **참조 컬럼 중 하나라도
`null` 이면 제약 검사를 건너뜁니다.** 즉 `(tour_area_code, tour_sigungu_code)` →
`regions` FK 를 걸어 두면, '전체' 선택('sigungu_code' null)은 그대로 통과하고
구를 지정한 경우에만 실재하는 구인지 검증됩니다. 여기에 `tour_area_code` 단독으로
`region_groups` FK 를 하나 더 걸면 시/도는 항상 유효합니다.

**제약을 걸 수 없어 비워 둔 자리가 없어집니다.**

### 그대로인 테이블

`trip_items` · `reservations` · `profiles` 는 컬럼이 바뀌지 않습니다. 다만
`trip_items.place_id` 와 `reservations.place_id` 가 `places` 를 `on delete cascade`
로 참조하므로 **교체 순서에 걸립니다**(아래 8번).

## 5. 수집 방안 — 구를 무엇으로 판정할 것인가

### 코드표는 만들지 않는다, 받는다 **[확정]**

`areaCode2` 는 코드 값이 아니라 **오퍼레이션(엔드포인트) 이름**입니다 — 끝의 `2` 는
이미 쓰고 있는 `areaBasedList2` · `detailCommon2` · `detailIntro2` 와 같은
KorService**2** 버전 표시입니다. 이 오퍼레이션이 코드표 자체를 내려줍니다.

```
areaCode2  (파라미터 없이)   → 시/도 17개 [코드, 이름]      → region_groups
areaCode2  (areaCode=N) ×17 → 시군구 전체 [코드, 이름]      → regions
areaBasedList2 (areaCode, sigunguCode, contentTypeId)     → places 후보
detailCommon2 / detailIntro2                              → 소개·영업시간·전화
```

**`areaCode` 값을 코드에 하드코딩하지 않습니다.** 관광공사가 지역코드를 실제로
이관한 사례가 있고(제주 장소 상당수가 적재에서 누락된 보고), 2026년 7월 광주·전남
통합 이후 코드를 다시 맞춘 사례도 여럿입니다. 매 수집마다 `areaCode2` 를 먼저 호출해
그 응답으로 두 테이블을 세우면 이 문제가 통째로 사라집니다.

### 구 판정 우선순위 **[확정]**

| 순위 | 방법 | `region_source` | 비고 |
|---|---|---|---|
| 1 | 응답의 `sigunguCode` | `'tour'` | 문자열이 아니라 코드라 통합·개칭에 안 흔들림 |
| 2 | **주소에서 시군구명 매칭** | `'addr'` | 시/도는 `areaCode` 로 이미 알고, 후보를 그 시/도의 시군구로 좁혀 찾음 |
| 3 | 좌표 → 행정구역 경계 point-in-polygon | `'geo'` | 2까지 실패한 잔여분. 경계 데이터가 필요함 **[미결 Q8]** |
| 4 | **미판정 코드로 격리** | `'unresolved'` | 다 실패한 행. 버리지 않고 수동 처리 대기열로 (아래) |

사람이 나중에 고친 행은 `'manual'` 이 됩니다(아래). 어느 순위로 판정됐는지가 행마다
남아 있어야 리포트가 "주소 매칭까지 걸러지고 남은 게 몇 건인지"를 셀 수 있습니다 —
Q8 이 그 숫자에 달려 있습니다.

**서울 실측(2026-09-22): 1,539건 전부 1순위로 판정됩니다.** `areacode`·`sigungucode`·
좌표가 빈 행이 **한 건도 없었습니다.** 2순위 주소 매칭조차 탈 일이 없었고 3순위는
더더욱입니다. 전국에서도 같다면 Q7·Q8 은 만들 필요가 없어집니다.

### 주소 파싱의 약점은 시/도 판정이지 시군구 판정이 아니다 **[확정]**

README 에 주소 파싱의 반례가 두 개 기록돼 있습니다. 세종은
`'세종특별자치시 한누리대로 288'` 처럼 행정동 없이 도로명이 바로 오고, 광주·전남은
`'전남광주통합특별시'` 로 통합돼 첫 토큰만으로 광주인지 전남인지 갈리지 않습니다.
**그런데 둘 다 시/도를 알아내는 문제입니다.**

우리가 푸는 건 다릅니다. `sigunguCode` 가 비는 장소는 대개 `areaCode` 는 들어 있어서
**시/도는 이미 알고 시군구만 모르는 상태**입니다. 그리고 시군구 이름은 주소에 그대로
있습니다 — `'서울특별시 강남구 테헤란로 1'`.

`areaCode2` 가 그 시/도의 시군구 이름 목록을 이미 줬으니 후보가 5~25개로 좁혀져
있습니다. 그 안에서만 비교하므로 `'서구'` 가 `'강서구'` 에 부분 문자열로 걸리는 문제도
**긴 이름 우선 매칭**으로 해결됩니다. 전국 229개를 상대로 맞출 때와는 난이도가 다릅니다.

그래서 주소 매칭을 2순위로 올립니다. 좌표 판정은 이것마저 안 되는 경우 —
`areaCode` 자체가 비었거나, 주소에 시군구명이 없거나(도로명만), 주소가 아예 없는
장소 — 를 위한 3순위입니다.

### 경계 데이터가 필요한 범위는 리포트가 알려준다

3순위에는 행정구역 경계 GeoJSON 이 필요하고, 무엇을 쓸지가 **[미결 Q8]** 입니다.
역지오코딩 API 대신 파일을 쓰는 이유는 외부 호출 없이 배치 안에서 끝나고 결과가
재현 가능하기 때문입니다 — 같은 파일로 다시 돌리면 같은 판정이 나옵니다.

**다만 정말 필요한지는 리포트를 봐야 압니다.** 2순위까지 걸러지고 남는 게 몇 건이면
경계 데이터를 구하지 않고 미판정으로 두어 손으로 처리하는 게 싸고, 수백 건이면
구하는 게 맞습니다.

어느 쪽을 쓰든 **매핑이 한 번 필요합니다.** 경계 파일이 주는 건 `'강남구'` 같은 이름이나
법정동코드이고 우리가 필요한 건 TourAPI `sigunguCode` 입니다. 229개뿐이라 한 번 만들어
검수하면 끝이고, 매칭이 실패한 건은 4순위로 떨어집니다.

### 판정 실패 시 — 존재하지 않는 코드로 격리한다 **[확정]**

코드도 없고 좌표 판정도 실패하는 행은 **반드시 생깁니다.** 이때 선택지는 셋인데
앞의 둘은 둘 다 나쁩니다.

- **버린다** — 왜 빠졌는지 아무 데도 안 남아, 나중에 "이 가게가 왜 없지"를 추적할 수 없습니다.
- **가장 가까운 구에 욱여넣는다** — 틀린 데이터가 맞는 데이터인 척 섞입니다. 사용자가
  강남구 필터로 찾은 장소가 실제로는 서초구인 상황이 조용히 만들어집니다.
- **존재하지 않는 코드로 등록한다** — 데이터는 남기되 사용자에게는 안 보이고,
  나중에 사람이 처리할 목록으로 쌓입니다.

세 번째로 갑니다.

**값은 음수를 씁니다.** TourAPI 의 `areaCode`·`sigunguCode` 는 항상 양의 정수라
음수는 절대 충돌하지 않습니다. `0` 이나 `99` 는 언젠가 실제 코드로 쓰일 수 있어
피합니다.

| 상황 | 저장되는 코드 |
|---|---|
| 시/도는 알고 구만 모름 (가장 흔함) | `(시/도 코드, -1)` |
| 시/도조차 모름 | `(-1, -1)` |

FK 가 걸려 있으므로 이 코드들도 **실재하는 행이어야 합니다.** `region_groups` 에
`tour_area_code = -1`, `name = '미판정'` 행 하나를 두고, `regions` 에는 시/도마다
`(N, -1)` 행을 하나씩 + `(-1, -1)` 행 하나를 둡니다. 수집 배치가 코드표를 받은 직후
이 행들을 함께 만듭니다.

**사용자에게는 보이지 않습니다.** 규칙은 하나입니다 — `tour_sigungu_code < 0` 인
지역과 그에 속한 장소는 드롭다운·지도·추천·플랜 어디에도 나오지 않습니다. 모든
화면이 `lib/db.ts` 한 모듈만 통해 데이터를 읽으므로(README), `places.list()` 와
`regions.list()` 두 곳에 제외 조건을 넣으면 전 화면에 적용됩니다. 별도 staging
테이블을 두는 방법도 있지만, 그러면 수동 처리가 "다른 테이블로 옮기기"가 되어
번거로워집니다. 지금 구조에서는 **코드 두 컬럼을 update 하는 순간 그 장소가 서비스에
등장하는** 편이 낫습니다.

### 미판정 행에 무엇이 저장되는가 **[확정]**

지역 코드만 `-1` 이 되고 **장소 정보는 전부 그대로 저장됩니다** — `id`(contentid) ·
이름 · 카테고리 · **주소** · **좌표** · 사진 · 소개 · 영업시간 · 전화. 관리자가 구를
판단하는 데 필요한 건 주소와 좌표인데 둘 다 행에 있으니, 목록을 열어 보고 올바른
코드 쌍을 넣으면 그 자리에서 끝납니다.

여기에 **왜 미판정이 됐는지**를 `region_note` 에 한 줄 남깁니다. 이게 없으면 관리자가
행마다 판정을 처음부터 다시 해봐야 합니다.

| `region_note` 예시 | 관리자가 할 일 |
|---|---|
| `sigunguCode 없음, 좌표 (37.5133, 127.0410) 어느 경계에도 미포함` | 주소를 보고 구를 직접 지정 |
| `sigunguCode 없음, 좌표가 경계 밖 (해상/섬)` | 인접 구 판단 또는 제외 |
| `코드=강남구 / 좌표=서초구 / 주소=서초구 — 3자 불일치` | 다수를 따르거나 원본 확인 |
| `areaCode 자체가 빈 값` | 시/도부터 지정 |

`region_source` 는 `'unresolved'` 가 됩니다. `'tour'`·`'addr'`·`'geo'` 는 자동 판정이
**성공한** 경로를 뜻하므로, 실패한 행을 그중 하나로 적어 두면 리포트에서 성공률이
부풀려집니다.

### 수동 처리한 값을 재수집이 덮어쓰지 않게 **[확정]**

처리용 관리 화면을 만들지는 **[미결 Q7]** 입니다.

여기에 함정이 하나 있습니다. 사람이 미판정 장소의 구를 손으로 고쳐 놓았는데 다음
재수집이 같은 행을 다시 `-1` 로 덮으면, 수동 작업이 통째로 날아가고 그 사실조차
드러나지 않습니다.

그래서 `region_source` 를 기준으로 삼습니다. **재수집 배치는
`region_source = 'manual'` 인 행의 지역 컬럼을 건드리지 않습니다.** 이름·사진·영업시간
같은 나머지 필드는 평소처럼 갱신합니다.

**`'manual'` 표시는 트리거로 자동화합니다.** 관리자가 코드만 고치고 `region_source` 를
바꾸는 걸 잊으면 다음 재수집이 그 행을 다시 `-1` 로 되돌리는데, 사람이 두 가지를
기억해야 하는 구조는 언젠가 깨집니다. **지역 코드가 바뀌면 `region_source` 를
`'manual'` 로 세우고 `region_note` 를 비우는 트리거**를 둡니다. SQL 로 직접 처리하기로
한 만큼(Q7) 더 그렇습니다 — update 문 하나로 끝나야 합니다.

배치가 스스로 쓰는 값은 트리거를 우회해야 하므로, 배치는 `region_source` 를 명시적으로
지정해 씁니다.

처리 대기열은 `tour_sigungu_code < 0` 또는 `region_source = 'unresolved'` 로 뽑습니다.

### 목표 밀도 **[미결 Q5]**

**수집 자체는 전국을 한 번에 돌립니다** — `areaCode2` 가 전국 코드표를 주므로 지역을
잘라 돌릴 이유가 없고, 자르면 어느 구가 비었는지도 알 수 없습니다.

밀도는 목표로 정하는 게 아니라 **수집 결과로 관측되는 값**입니다. 하루 플랜이
5곳이니 조합이 생기려면 구당 최소 10곳이 필요한데, TourAPI 가 실제로 그만큼 갖고
있는지는 지역마다 다릅니다. 리포트의 구별 장소 수를 보고 **어디를 보강할지**를
정하는 것이 Q5 입니다 — 수집 범위가 아니라 보강 우선순위입니다.

보강이 필요하다면 수요가 몰리는 순서(서울 → 6대 광역시 → 경기·인천 → 나머지)가
자연스러운 후보이지만, 리포트를 보기 전에 못 박지 않습니다.

## 6. 외부에서 받아온 평점과 우리가 만든 평점을 나눈다 **[확정]**

지금 `places.rating` 은 `not null default 0` 이고, TourAPI 가 평점을 주지 않으므로
**339곳 전부 0** 입니다. 이 하나의 필드가 두 가지 일을 동시에 망치고 있습니다.

- 화면 네 곳(`PlaceCard` · `ExplorePage` · `PlaceDetailPage` · `RecommendPage`)이
  `rating.toFixed(1)` 을 그대로 찍어 **모든 장소가 `★ 0.0` 으로 보입니다.**
  "평점 없음"과 "0점"이 구분되지 않아서 생긴 일입니다.
- `db.ts` 의 장소 목록이 `order('rating', desc)` 로 정렬하는데 전부 같은 값이라
  정렬이 사실상 무작위입니다. `HomePage` 에는 이미 이걸 우회하는 주석과 코드가
  들어가 있습니다.
- 추천 점수식(`recommend.ts`)이 `place.rating * 2` 를 기본 점수로 쓰는데 그 항이
  통째로 0이라, 추천이 취향 태그와 시간대/날씨 보너스만으로 돌아갑니다.

그래서 필드를 성격별로 나눕니다.

| | 무엇 | 누가 쓰나 | 재수집이 |
|---|---|---|---|
| `places.source_rating` | 외부(TourAPI)가 준 평점. **주지 않으면 `null`** | 수집 배치 | 자유롭게 덮어씀 |
| 내부 평점 (별도) | 사용자 리뷰(`trip_items.rating`)를 집계한 값 | 앱 | **건드리지 않음** |

`0` 이 아니라 `null` 이어야 합니다. 그래야 화면이 "평점 없음"일 때 별점을 아예
**표시하지 않기로** 결정할 수 있고, 정렬·추천도 "신호 없음"을 명시적으로 다룰 수
있습니다. `region_source` 로 판정 출처를 남긴 것과 같은 원칙입니다 — **받아온 값과
만든 값을 같은 칸에 넣지 않습니다.**

### `tags` 도 같은 문제이고, 이번에도 비어 있다

`places.tags` 는 339곳 전부 빈 배열입니다 — TourAPI 에 취향 태그와 맞출 신뢰할 원천이
없어 추측해 채우지 않았다고 README 가 적어뒀습니다. **재수집해도 그대로입니다.**

추천 점수식은 `rating × 2` 를 기본 점수로 쓰고 취향 태그 매칭으로 가점하는데, **두
항이 동시에 죽어 있습니다.** 그래서 지금 추천은 실질적으로 시간대·날씨 보너스만으로
순서를 정하고 있습니다. 이 구조를 어떻게 할지는 내부 평점 집계와 함께 별도 intent 로
다룰 일이고, 이번 문서에서는 **`tags` 를 빈 배열로 두는 것만 확정합니다 [확정]** —
없는 데이터를 추측해 채우지 않는다는 README 의 판단을 유지합니다.

### 내부 평점 집계는 이번 범위가 아니다 **[확정]**

집계를 어디에 둘지는 간단하지 않습니다. `trip_items` 는 RLS 로 본인 행만 보이므로
단순한 뷰로 집계하면 **사용자마다 자기 리뷰만 평균한 값**이 나옵니다. 전역 집계를
하려면 `security definer` 함수로 계산해 `places` 에 캐시 컬럼을 두거나, 리뷰를
`trip_items` 에서 공개 테이블로 분리해야 합니다. 후자는 플랜 공유와 맞물리는
설계라 여기서 정할 일이 아닙니다.

**이번 문서에서는 분리만 확정합니다** — `source_rating` 으로 이름과 의미를 고정하고,
내부 평점 집계는 별도 intent 로 뺍니다. 다만 재수집과 **함께 해야 하는 것**이 하나
있습니다: `source_rating` 이 `null` 일 때 화면에서 별점을 숨기고 정렬 기준을 바꾸는
일입니다. 이걸 미루면 교체 후에도 `★ 0.0` 이 계속 보입니다.

## 7. 카테고리 기울기 **[확정]**

술집(`sulzip`)은 전국 4곳입니다. **서울 수집으로 이게 데이터 부족이 아니라 분류
자체의 부재임이 확인됐습니다.**

서울 음식점 968건의 분류가 이렇습니다.

| `lclsSystm2` | 건수 | | `cat3` | 건수 |
|---|---|---|---|---|
| FD01 | 485 | | A05020100 한식 | 507 |
| FD02 | 303 | | A05020200 양식 | 122 |
| FD03 | 45 | | A05020300 일식 | 86 |
| FD05 | 135 | | A05020400 중식 | 73 |

**서울 전체에 주점이 한 건도 없습니다.** README 가 적어둔 "FD04 전 지역 0건"이

`A050207xx`, 카페는 `A05020900`, 술집은 해당 코드 없음, 명소는 contentTypeId 12·14.

## 8. 교체 순서 **[확정]**

**첫 적재와 이후 재수집은 규칙이 다릅니다.** 같은 배치가 두 가지 일을 하는 게
아니라, 삭제는 첫 적재에만 있는 단계입니다.

### 첫 적재 — 전부 지우고 새로

문자열 목적지를 코드로 옮기는 매핑은 만들지 않습니다. `places` → `regions` →
`region_groups` 역순으로 비우고, `region_groups` → `regions` → `places` 순으로
채웁니다. `regions` 가 `places` 의 참조 대상이라 항상 먼저입니다.

**여기서는 중간에 실패해도 위험이 없습니다.** 지울 가치가 있는 데이터가 없고,
카탈로그가 잠시 비어도 보는 사람이 없습니다. 실패하면 그냥 다시 돌립니다.

### 이후 재수집 — 지우지 않고, 바뀐 것만 다시 받는다 **[확정]**

2회차부터는 **삭제 단계가 없습니다.** `contentid` 기준으로 upsert 하고, 마지막에
"이번 응답에 없고 `trip_items`·`reservations` 어디에서도 참조되지 않는 행"만 골라
지웁니다. `region_source = 'manual'` 인 행의 지역 컬럼은 건드리지 않습니다(5번).

그리고 **상세를 전부 다시 받지 않습니다.** TourAPI 목록 응답에 `modifiedtime` 이
들어 있고, 실측으로 **15,518건 100%에 채워져 있음을 확인했습니다.** 수집 시점의 그
값을 상세와 함께 저장해 두면, 재수집은 이렇게 됩니다.

1. 목록만 받는다 (약 700 호출)
2. 저장된 `modifiedtime` 과 비교한다
3. **새로 생겼거나 값이 바뀐 곳의 상세만** 다시 받는다

서울 실측의 수정 연도 분포가 2024년 155 · 2025년 13,912 · 2026년 1,451 이라, 한 해에
갱신되는 비율이 10% 안팎입니다. 첫 수집이 약 31,000 호출인 데 비해 **2회차는 목록 700
+ 상세 수천 호출**로 끝납니다. 전량 재수집과 증분 갱신의 차이가 한 자릿수 배가 아니라
열 배 규모입니다.

이렇게 하면 **라이브 카탈로그가 비는 순간이 아예 없습니다.** 재수집이 중간에
실패해도 앱은 직전 데이터로 계속 돌아가고, 다시 돌리면 이어서 채워집니다. 첫
적재에만 있던 위험 구간이 구조적으로 사라집니다.

`places` 에 `source_modified_at` 컬럼을 두어 이 값을 DB 에도 남깁니다 — 적재 단계에서
"무엇이 바뀌었는지"를 판단하는 근거가 되고, 수집 파일이 없어도 증분 갱신이 됩니다.

**삭제·미표출 콘텐츠는 아직 정확히 다루지 못합니다.** 관광공사에 동기화 전용
오퍼레이션이 따로 있어 `showflag`(표출 여부)를 준다고 알려져 있으나, 지금 쓰는
`detailCommon2` 응답에는 없습니다. 2회차 재수집을 실제로 설계할 때 확인할 일이고,
그때까지는 "이번 응답에 없는 행"을 삭제 후보로 보는 현재 방식으로 갑니다.

### 수집과 적재를 분리한다

두 시점 모두 **TourAPI 호출을 전부 끝내 파일로 떨어뜨린 뒤, 그 파일에서 적재**합니다.
호출 중간에 429나 네트워크 오류가 나도 DB 는 손대지 않은 상태로 남고, 적재는 파일만
읽으니 한 트랜잭션으로 짧게 끝납니다. 재수집도 파일부터 다시 만들면 되니 반복이
쌉니다.

첫 적재에는 이 구조가 굳이 필요하지 않지만, 그때 같이 만들어 두는 편이 낫습니다 —
정작 필요해지는 재수집 시점에는 급해서 안 만들게 됩니다.

적재는 한 행씩 넣지 않고 `on conflict do update` 로 수십~수백 건씩 묶습니다. 거부된
행이 있으면 **멈추지 않고 건너뛰고 실패 목록을 리포트에 남깁니다** — 미판정을 다루는
방식과 같습니다(5번).

### 배치는 어디 두고 어떻게 돌리는가 **[확정]**

- **위치** — 이 문서와 같은 디렉토리(`intent/2026-09-20-재수집-스키마-교체/`). 앱
  빌드와 무관한 1회성 도구이므로 `src/` 에 넣지 않습니다. 저장소에는 들어가되
  "문서에 딸린 재현 수단"으로 둡니다. 프로젝트 README 의 "수집 스크립트는 저장소에
  포함돼 있지 않습니다" 문장은 이 결정에 맞게 고쳐야 합니다.
- **파일** — `collect.mjs`(목록 + 상세 수집, 의존성 없는 Node 스크립트) · `README.md`(실행법) ·
  `.gitignore`(`raw/` 는 커밋하지 않고 `raw/report.json` 만 남김). 적재 스크립트는
  Q4 가 DDL 에 걸려 있어 아직 없습니다.
- **키** — 파일에도, `.env` 에도 넣지 않고 **실행할 때 입력받습니다.** 커밋 diff 에
  공공데이터 API 키가 섞일 경로를 아예 만들지 않기 위한 것입니다(CLAUDE.md).
- **실행** — 첫 적재용입니다. 일일 호출 한도 때문에 며칠에 걸쳐 여러 번 이어서
  실행될 수 있고, 재개는 이미 받은 것을 건너뛰는 방식입니다. 2회차 재수집이
  필요해지면 그때 별도로 다룹니다.

### 나누는 단위 — 개수가 아니라 시군구 **[확정]**

100건, 1000건 같은 **개수 단위로 자르지 않습니다.** 시군구 하나를 한 덩어리로
삼습니다. 이유가 셋입니다.

1. API 파라미터가 `areaCode` + `sigunguCode` 단위라 경계가 이미 거기 있습니다.
2. 실패·재개 경계가 그대로 파일 경계가 됩니다 — 시군구당 파일 하나를 쓰고,
   **이미 파일이 있는 시군구는 건너뜁니다.** 상세는 그 파일 안에서 장소 단위로
   더 촘촘하게 재개합니다(아래). 며칠에 걸쳐 나눠 돌려도 안전합니다.
3. 리포트가 구별 밀도를 보는 것이라 집계 단위가 일치합니다.

페이지 크기(`numOfRows`)는 **100** 으로 둡니다. 기본값이 10이라 지정하지 않으면
호출이 10배로 늘고, 1000 같은 큰 값은 응답이 무거워져 타임아웃 사례가 보고돼
있습니다. 어차피 시군구당 수십 곳이면 대개 한 페이지로 끝나므로 페이지 크기는
큰 변수가 아닙니다.

호출 사이에 짧은 지연을 둡니다(초당 5~10건 수준). 한 번 돌리고 끝나는 배치에서
속도를 욕심낼 이유가 없고, 429 를 받으면 지수 백오프로 물러납니다.

### 목록과 상세를 한 배치에서 받는다 **[확정]**

`areaBasedList2`(목록)는 장소당 이름·주소·좌표·사진·카테고리 코드를 줍니다.
`summary`(소개)는 `detailCommon2`, `open_hours`·`phone` 은 `detailIntro2` 에 있어서
장소마다 2회를 더 호출해야 합니다. **그 둘까지 같은 배치에서 받습니다.**

**실측(2026-09-22): 전국 목록 수집 완료. 234개 시군구, 15,518곳.**

| | 호출 수 |
|---|---|
| 코드표 (`areaCode2`) — 시/도 1 + 시군구 17 | 18 |
| 목록 (`areaBasedList2`) — 234개 시군구 × 콘텐츠타입 3 | 약 700 |
| 상세 (`detailCommon2` + `detailIntro2`) — 15,518곳 × 2회 | **약 31,000** |
| 합계 | **약 31,700** |

시/도별로는 경기 3,362 · 강원 1,628 · 서울 1,539 · 경남 1,266 · 경북 1,195 순입니다.
처음 추정했던 3,000곳의 다섯 배이고, 상세가 전체 호출의 98%를 차지합니다.

한 번에 다 받아두면 `places` 가 처음부터 온전하게 채워지고, 나중에 "상세만 채우는
2차 작업"이라는 별도 과제가 생기지 않습니다. 지금 DB 의 339곳은 이미 상세가 채워져
있는데, 목록만 받았다면 교체 후 그 장소들의 정보가 오히려 줄어들었을 것입니다 —
그 문제도 함께 사라집니다.

### 그래서 며칠에 걸쳐 돌아간다

**실제 한도는 아직 모릅니다.** 서울 상세가 2,100 호출쯤에서 한 번 멈췄지만 같은 날
오후에 다시 호출이 됐으므로 일일 한도로 단정할 수 없습니다 — 시간당 제한이나 일시적
오류였을 수 있습니다. 정확한 값은 공공데이터포털 마이페이지의 개발계정 상세보기에
나옵니다.

31,000 호출이 며칠짜리인지는 그 숫자가 나와야 계산됩니다. 한도가 2,000이면 보름,
10,000이면 사흘입니다.

재개 구조가 있으니 며칠에 걸쳐 돌아가는 것 자체는 문제가 아니고, `run-daily.sh` 와
launchd 로 무인 실행도 됩니다. 다만 이 규모에서는 **운영계정 전환이 사실상 필요합니다**
— 키를 새로 받는 절차가 아니라 같은 키의 한도를 올리는 것입니다.

다만 재개 단위가 목록보다 촘촘해야 합니다. 상세는 시군구당 최대 200회(100곳 × 2)라,
시군구 단위로만 재개하면 중간에 죽을 때 최대 200회를 다시 씁니다. **이미 받은
`contentid` 는 건너뛰도록 장소 단위로 기록합니다.**

### 상세가 비는 장소는 여전히 있다

상세를 받아도 TourAPI 가 `overview`·영업시간·전화를 **주지 않는 장소가 섞여 있습니다.**
받아봐야 몇 퍼센트인지 알 수 있고, 리포트가 그 비율을 알려줍니다(14번).

그래서 화면 처리는 여전히 필요합니다 — `source_rating` 을 null 로 둔 것과 같은
원칙으로, **값이 없으면 그 영역을 아예 숨깁니다.** 빈 제목과 빈 칸이 남은 화면은 그 영역이
아예 없는 화면보다 나쁩니다(9번). `phone` 이 없으면 전화 연결 버튼은 노출되지
않습니다 — 지금도 조건부로 붙는 버튼입니다.

## 9. 앱 코드 영향 범위

### 먼저, 사람이 읽는 지역 이름이 사라진다 **[확정]**

지금은 `place.region` 자체가 `'서울 성동구'` 라서 어디서든 그냥 출력하면 됐습니다.
코드로 바꾸면 **표시하는 모든 지점이 변환을 거쳐야 합니다.** 그리고 그 지점은 화면만이
아닙니다 — `lib/share-card.ts` 가 `place.region` 을 인스타그램 해시태그로 쓰고 있어서,
변환을 놓치면 사용자 게시물에 `#-1` 같은 게 나갑니다.

그래서 "클라이언트에 변환 맵을 두고 필요한 곳에서 부른다"로 가지 않습니다. 놓치는
곳이 반드시 생깁니다. **`lib/db.ts` 의 장소·여행 조회가 `regions` 를 조인해
`region_name`(과 `group_name`)을 함께 반환합니다.** 모든 화면이 `db.ts` 한 모듈만
통해 읽으므로(README), 반환 타입에 이름이 들어오면 표시 지점은 거의 손대지 않아도
되고 새로 생기는 표시 지점도 자동으로 안전합니다.

### 파일별

| 파일 | 무엇이 |
|---|---|
| `lib/types.ts` | `RegionGroup`·`Region`·`Place`·`Trip` 인터페이스 |
| `lib/db.ts` | `PlaceFilter` 가 지역을 **이름**으로 받음 → 코드 쌍으로. 조회에 `region_name` 조인 추가 |
| `hooks/useRegions.ts` | 2단 드롭다운 구성이 `group_name` 문자열 매칭 → 코드 매칭 |
| `lib/seed.ts` | `DEMO_REGION_GROUPS`·`DEMO_REGIONS`·`SEED_PLACES` |
| `lib/share-card.ts` | `place.region` 을 해시태그로 사용 — **놓치면 사용자 게시물에 코드가 나감** |
| `pages/TripCreatePage.tsx` | 목적지 2단 드롭다운, `defaultTripTitle()`, `'전체'` 선택 시 상위 지역명으로 저장하던 처리 |
| `pages/TripRulesPage.tsx` | `destination` 이 leaf 인지 group 인지 이름으로 판별하던 로직 — **`sigungu_code == null` 로 바뀌어 오히려 단순해짐** |
| `pages/ExplorePage.tsx` | 지역 필터, URL 파라미터, 내 위치 최근접 지역 판정 |
| `pages/RecommendPage.tsx` | 추천 지역 선택, 다가오는 여행 목적지 자동 설정 |
| `pages/PlaceDetailPage.tsx` | `{place.region}` 을 두 곳에서 직접 출력. `summary`·`open_hours` 가 빈 값일 때 그 영역을 숨김 (8번) |
| `pages/RoutePage.tsx` | `{trip.destination}` 을 subtitle 로 출력 |
| `lib/recommend.ts` | 점수식의 `place.rating * 2` — `source_rating` 이 null 이 되면 이 항을 어떻게 다룰지 정해야 함 |
| `components/PlaceCard.tsx` | `★ {rating.toFixed(1)}` — null 이면 숨김. 한 줄 소개가 빈 값일 때 자리를 차지하지 않게 |
| `pages/HomePage.tsx` | rating 이 전부 0인 걸 우회하던 로직 — 정리 대상 |

별점을 화면에 찍는 곳은 `PlaceCard` · `ExplorePage` · `PlaceDetailPage` ·
`RecommendPage` 네 곳이고, 정렬은 `db.ts` 의 `order('rating')` 입니다 — 6번의 결정이
이 다섯 군데를 건드립니다.

`lib/geo.ts`(거리·동선 계산)는 좌표만 쓰므로 영향 없습니다.

## 10. 데모 모드 **[확정]**

README 가 `.env` 없이 모든 화면이 동작한다고 약속하고 있습니다. `seed.ts` 의 데모
지역·장소를 새 코드 체계로 같이 갱신하지 않으면, 데모 모드에서만 옛 지역이 나오는
상태가 됩니다. 전량을 넣을 필요는 없고 **서울 몇 개 구 + 제주 + 부산** 정도면
드롭다운 2단 동작과 필터를 확인하기에 충분합니다.

## 11. 플랜 공유 기능과의 순서 **[확정]**

**이 작업이 먼저입니다.** 플랜 공유의 `shared_plan_items` 가 `places` 를 FK 로
참조하므로, 공개 플랜이 쌓인 뒤에 카탈로그를 갈아엎으면 남의 플랜에서 장소가
사라집니다. 공유 기능이 아직 없는 지금이 재수집을 끝내기에 가장 조용한 시점입니다.

덤으로, 공유 문서의 "확인이 필요한 사실" 첫 항목(카탈로그만으로 공유할 만한 플랜이
나오는지)에 대한 답이 이 작업의 결과로 나옵니다.

## 12. 열린 질문

번호는 한 번 부여하면 바꾸지 않습니다(본문 표시와 어긋나므로). 닫힌 질문은 줄을
지우되 번호는 재사용하지 않습니다. **해소됨: Q1**(미판정 코드가 null 허용 문제를
없앰) · **Q3**(기존 데이터 전부 삭제로 결정) · **Q9**(목록과 상세를 한 배치에서
함께 받기로 결정) · **Q4**(법정동코드를 이번에 같이 넣기로 **뒤집음** — 응답에 100% 들어 있었음) ·
**Q2**(광주·전남이 별개로 내려와 분리 유지에 작업 불필요) · **Q6**(서울에서도 주점
분류 0건 — 이번엔 그대로 두고 별도 과제).

**남은 세 건은 전국 수집이 끝나야 닫힙니다.** 서울만으로는 세 건 다 "불필요" 쪽으로
기울었지만(미판정 0건, 25개 구 전부 충분한 밀도), 지방 군 단위는 사정이 다를 수
있습니다. 표가 비면 스키마와 적재를 확정합니다.

## 13. 수용 기준

괄호 안의 Qn 은 그 질문이 닫혀야 판정 기준이 확정되는 항목입니다.

- [ ] `regions.name` 에 시/도 접두어가 없고, 서울 강서구와 부산 강서구가 동시에 존재한다
- [ ] `trips` 에서 '시/도 전체'를 선택한 여행이 `tour_sigungu_code` null 로 저장되고 FK 위반이 나지 않는다
- [ ] 존재하지 않는 구 코드 쌍으로 여행을 만들려는 시도가 FK 에서 막힌다
- [ ] 참조 무결성이 보장되지 않는 지역 컬럼이 스키마에 남아 있지 않다
- [x] 서울에서 장소 10곳 이상인 구가 20개 이상이다 — 25개 전부 (수집으로 확인)
- [ ] `regions.ldong_cd` 가 채워지고, 같은 시군구 안에서 장소들이 보낸 값이 서로 일치한다
- [ ] 배치가 14번의 리포트 항목을 전부 남긴다
- [ ] `sigunguCode` 가 빈 행이 주소의 시군구명 매칭으로 올바른 구에 들어갔다
- [ ] 같은 시/도 안에서 `'서구'` 와 `'강서구'` 가 뒤섞이지 않는다 (긴 이름 우선 매칭)
- [ ] 판정에 실패한 장소가 버려지지도, 엉뚱한 구에 들어가지도 않고 `-1` 코드로 남아 있다
- [ ] 미판정 지역과 그에 속한 장소가 드롭다운·지도·추천 어디에도 보이지 않는다
- [ ] 행마다 `region_source` 가 실제 판정 순위와 일치한다 (성공률이 부풀려지지 않는다)
- [ ] 교체 후 로그인한 사용자에게 '나의 여행'의 빈 상태 화면이 정상적으로 보인다
- [ ] 미판정 장소의 코드를 손으로 고치면 별도 작업 없이 서비스에 바로 등장한다
- [ ] 미판정 행에 주소·좌표를 포함한 장소 정보가 전부 남아 있다
- [ ] 미판정 행마다 `region_note` 에 사유가 적혀 있어, 다시 조사하지 않고 판단할 수 있다
- [ ] 지역 코드만 update 해도 `region_source` 가 `'manual'` 로 자동 전환된다
- [ ] `region_source = 'manual'` 인 행의 지역이 재수집을 다시 돌려도 유지된다
- [ ] 코드·주소·좌표 세 판정이 불일치한 행 목록이 남아 있고, 전부 사람이 확인됐다
- [ ] 비로그인(Guest) 상태에서 지도 탭의 지역·장소가 그대로 보인다 — RLS 재생성 확인
- [ ] 화면과 공유 캡션 어디에도 지역 코드 숫자가 노출되지 않는다 (해시태그 포함)
- [ ] 평점이 없는 장소에 `★ 0.0` 이 표시되지 않는다 (네 화면 전부)
- [ ] 장소 목록 정렬이 `source_rating` 에 의존하지 않는다
- [ ] TourAPI 가 소개·영업시간을 주지 않은 장소의 상세 화면에 빈 제목이나 빈 칸이 남지 않는다
- [ ] `phone` 이 없는 장소에 전화 버튼이 나오지 않는다
- [ ] 데모 모드(`.env` 없음)에서 2단 드롭다운과 지역 필터가 동작한다
- [ ] 재수집 배치를 두 번 돌려도 결과가 같다 (멱등)
- [ ] 재수집이 중간에 실패해도 앱이 직전 카탈로그로 계속 동작한다 (삭제 단계가 없음)
- [ ] 적재 중 거부된 행이 배치를 멈추지 않고 리포트에 남는다
- [ ] 배치를 중단하고 다시 실행하면 이미 받은 시군구와 이미 받은 장소 상세를 건너뛰고 이어서 받는다
- [ ] 일일 호출 한도에 걸려 죽어도 다음 실행이 이어서 받는다
- [ ] 배치 파일과 커밋 diff 어디에도 공공데이터 API 키가 없다
- [ ] `npx tsc --noEmit` · `npm run build` 통과
- [ ] 검증에 쓴 테스트 계정과 그 계정이 만든 행만 정확히 지정해 삭제했고, 실제 사용자 데이터는 그대로다

## 14. 수집 리포트가 답할 것들 **[확정]**

사전에 사람이 API 응답을 눈으로 확인하는 절차는 두지 않습니다. 미판정 장치가 이미
있으니 **배치를 돌리는 것 자체가 확인**이고, 데이터는 앞으로도 계속 추가될 테니
한 번 본 결과는 다음 재수집 때 유효하지 않습니다.

대신 **배치가 마지막에 리포트를 남깁니다.** 미판정으로 쌓아두는 전략은 "누군가 그
목록을 본다"를 전제하는데, 리포트가 없으면 쌓이는 걸 아무도 모릅니다.

| 리포트 항목 | 무엇을 정하는 데 쓰나 |
|---|---|
| 시/도별 · 구별 장소 수 | 1단계 범위와 목표 밀도 (Q5) |
| 미판정(`-1`) 건수와 그 목록 | 수동 처리 규모, 관리 화면 필요 여부 (Q7) |
| 판정 경로별 비율 (`tour` / `addr` / `geo` / `unresolved`) | 어느 순위까지 내려가는지 |
| 미판정 사유별 분포 (`region_note` 유형) | 어떤 실패가 많은지 — 판정 로직을 고칠지 사람이 처리할지 |
| `addr` 까지 걸러지고 남은 건수 | 경계 데이터를 구해야 하는지 (Q8) |
| 코드·주소·좌표 3자 불일치 목록 | 사람이 확인할 대상 |
| 적재에서 거부된 행 목록 | 스키마·제약과 어긋난 데이터 |
| 상세 수집률과 `overview`·영업시간·전화가 실제로 채워진 비율 | 화면에서 빈 영역을 얼마나 숨겨야 하는지 |
| 시/도 목록과 이름 표기 원문 | 광주·전남이 어떻게 내려왔는지 (Q2) |
| 카테고리별 장소 수 | 술집 보충 판단 (Q6) |

### 서울 실측 (2026-09-22)

시/도 이름은 **표기가 섞여서 옵니다 [확정: 축약 규칙 필요]**.

```
1=서울  2=인천  3=대전  4=대구  5=광주  6=부산  7=울산
8=세종특별자치시  31=경기도  32=강원특별자치도  33=충청북도  34=충청남도
35=경상북도  36=경상남도  37=전북특별자치도  38=전라남도  39=제주특별자치도
```

광역시 7개는 축약형인데 나머지 10개는 정식 명칭입니다. 현재 `region_groups` 는
`경기`·`강원`·`충북` 같은 축약형이므로 **10개에 축약 규칙이 필요합니다.** 받은 그대로
넣고 나중에 고쳐도 되는데, 키가 코드로 바뀐 덕에 `name` 은 update 한 번이면 됩니다 —
예전 구조에서는 이름 변경이 FK 연쇄였고, 그게 코드 PK 로 얻은 두 번째 이득입니다.

**광주(5)와 전남(38)은 별개로 내려옵니다.** 2026년 7월 통합이 TourAPI 코드에는 반영돼
있지 않아, 분리 유지에 아무 작업이 필요 없습니다(Q2 닫힘).

그 밖에 서울에서 확인된 것: 1,539건 전부 판정 1순위로 해결(미판정 0건), 상세 충족률
소개 99.9% · 전화 98.6% · 영업시간 97.4%, 25개 구 전부 장소 10곳 이상, 주점 분류 0건,
**법정동코드 100% 포함**.

경계 데이터를 구하기로 한다면(Q8) **스냅샷 시점을 반드시 확인해야 합니다** — 2026년
7월 개편(인천 3개 구 신설, 광주·전남 통합)이 반영된 버전이어야 합니다. 공공데이터포털에
올라와 있는 SGIS 행정구역 경계 파일은 스냅샷이 2025-06-30 기준이고, GitHub 재배포본은
