# 플로차트 규칙을 코드에서 따로 관리하기 — 진단 · 방안

> 다른 화면: [홈](홈.md) · [지도](지도.md) · [추천](추천.md) · [새 여행 만들기](여행-만들기.md) · [동선 최적화](동선-최적화.md) · [장소 업데이트](장소-업데이트.md) · [목록](../README-플로챠트.md)
>
> 화면 문서(`플로챠트/*.md`)의 흐름 · 규칙 표가 코드 어디에 있는지 바로 찾고, 문서를 고칠 때 코드도
> 빠짐없이 고치기 위한 방안입니다. 화면 문서가 아니라 **가이드**입니다 — 채택한 것은 `CLAUDE.md` 로 옮깁니다.
> 처음 안(3계층 · `features/`)을 실제 코드와 대조해(10/10) 맞지 않는 곳을 고치고 범위를 줄였습니다.

## 1. 지금 코드 — 대조한 결과

### 이미 나뉘어 있는 것

규칙의 절반쯤은 이미 화면 밖 순수 함수입니다. 새 폴더를 만들기보다 **이것을 기준 자리로 삼습니다.**

| 파일 | 담은 규칙 | 화면 문서 |
|---|---|---|
| `src/lib/recommend.ts` | 별점 점수(`ratingScore`) · 순위(`rankAll`) · 한 쪽 고르기(`takePage`) · 자동 담기(`pickByRating`) | 추천 · 새 여행 만들기 |
| `src/lib/geo.ts` | 최단 동선(`optimizeOrder`) · 이동 시간(`routeMinutes` · `dayTripTravel`) · 위치 재기(`locate`) · 반경 상수 | 동선 최적화 · 홈 · 지도 |
| `src/lib/map-group.ts` | '+N' 묶기(`groupRepresentatives` · `groupOverlapping`) | 지도 |
| `src/lib/trip-date.ts` | 날짜 표시 | 여러 화면 |

### 고칠 점 (중요한 순)

1. **SQL 과 TS 에 같은 규칙이 두 벌** — 가장 큰 어긋남 위험입니다. 지금은 주석("바꾸면 함께")으로만 묶여 있습니다.

   | 규칙 | DB 함수 | 앱(데모 · 라벨) |
   |---|---|---|
   | 추천 점수 · 한 쪽 | `recommend_places()` | `ratingScore` · `takePage` |
   | 홈 고르기 · 반경 | `home_picks()` | `demoHomeOrder` · `DAY_TRIP_RADIUS_KM` |
   | 가까운 100곳 | `places_nearest()` | `places.nearest` 데모 분기 |

   둘이 같은지 확인한 스크립트(테스트 DB 에서 쪽마다 비교)는 저장소 밖에만 있습니다.
2. **날짜 버그 — 한국 시각 0~9시에 하루 밀림.** `toISOString().slice(0, 10)` 은 UTC 날짜라, 새벽에 새 여행을
   만들면 기본 날짜가 +7일이 아니라 +6일, '다가오는 여행'은 어제 여행까지 포함합니다. 같은 코드가 세 곳 —
   `TripCreatePage`(새 여행 기본 날짜) · `PlanDetailPage`(코스 담기 기본 날짜, 같은 `todayIso` 를 복사해 둠) ·
   `RecommendPage`(다가오는 여행 고르기). → **고침(10/10, 1단계)** — `trip-date.ts` 의 `kstDate()` ·
   `upcomingTrip()` 하나로. 같이 찾은 것: 홈 '다가오는 여행' 카드가 날짜가 가장 늦은 여행(`myTrips[0]`)이라
   지난 여행이 뜨거나 가장 먼 여행이 떴다 — 오늘 이후 가장 빠른 여행으로 고침.
3. **'화면 기억' 패턴이 다섯 벌** — `savedPicks` · `savedFeed` · `savedCourses` · `unsavedOrder` · `savedFilters` 가
   각자 모듈 변수 · 10분 만료 · 키 비교를 따로 구현합니다. 만료 시간 · 키 규칙을 바꿀 때 다섯 곳을 고쳐야 합니다.
4. **규칙 번호가 바뀐다** — 문서 규칙 표의 번호는 줄을 넣거나 빼면 밀립니다(10/10 새 여행 만들기 13 → 12).
   코드 주석에 `규칙 #12` 처럼 번호를 박으면 바로 틀린 주석이 됩니다.
5. **테스트 러너가 없다** — `package.json` 에 vitest · jest 가 없어, 순수 함수로 나뉜 규칙도 검사하지 못합니다.
6. 자잘한 중복 — `ALL_LEAF = ''` 4곳, `PAGE_SIZE = 10` 3곳.

## 2. 처음 안 검토

처음 안(3계층 Rule · Flow · View, `src/features/<화면>/`)의 방향은 맞지만 그대로 옮기면 안 되는 곳이 있습니다.

| 처음 안 | 대조 결과 | 바꾼 방향 |
|---|---|---|
| 화면마다 `src/features/<화면>/` | `src/lib/` 에 이미 규칙 모듈이 있어 두 갈래가 된다 | 화면 규칙은 `src/rules/<문서 이름>.ts` 하나로, 공통 규칙은 `src/lib/` 그대로 |
| 모든 화면에 `useXxxFlow` 훅 | 화면 상태 · 이펙트를 통째로 옮기면 파일만 둘이 되고 읽기는 비슷하다 | 훅은 하지 않는다. 규칙 · 파이프라인만 꺼낸다 |
| 예시 `TripDraft` 의 `area_code` · `sigungu_code` · `start_date` | 실제 칸은 `tour_area_code` · `tour_sigungu_code` · `trip_date` | 아래 예시는 실제 코드 기준 |
| 예시 날짜 `d.toISOString().slice(0, 10)` | 위 2번 버그를 그대로 옮김 | 한국 날짜 함수 하나(`kstDate`)로 |
| 예시 `<StepGuide currentStep totalSteps>` | 실제는 `steps` · `current` | — |
| 주석에 `규칙 #11` | 번호가 밀린다(위 4번) | 고정 규칙 ID(아래 3-2) |
| "240줄 → 80줄" | 근거 없음 — 화면 대부분은 마크업 | 줄 수 목표는 두지 않는다 |
| SQL ↔ TS 이중 구현 | 언급 없음 | 가장 먼저(아래 3-4) |

## 3. 방안

### 3-1. 자리 — 문서 하나 = 규칙 파일 하나

```text
src/
├── lib/                 # 여러 화면이 같이 쓰는 규칙 (그대로)
│   ├── recommend.ts     #   별점 · 순위 · 자동 담기
│   ├── geo.ts           #   거리 · 동선 · 위치
│   ├── map-group.ts     #   '+N' 묶기
│   ├── trip-date.ts     #   한국 날짜 kstDate · 다가오는 여행 upcomingTrip (1단계에서 더함)
│   └── screen-memory.ts #   새로 — 화면 기억(만료 · 키)
└── rules/               # 새로 — 플로챠트 문서 하나에 파일 하나, 그 화면만의 규칙
    ├── trip-create.ts   #   플로챠트/여행-만들기.md
    ├── home.ts          #   플로챠트/홈.md
    ├── route.ts         #   플로챠트/동선-최적화.md
    └── *.test.ts        #   규칙 표를 그대로 옮긴 검사
```

규칙 파일에 넣는 것: 상수(개수 · 시간 · 반경 · 구성), 순수 함수(제목 · 판정 · 고르기), 저장까지 묶인
**파이프라인**(예: 자동 담기 — DB 호출을 인자로 받거나 `db.ts` 를 부른다). 넣지 않는 것: React 상태 · 이펙트 · 마크업.

예 — `src/rules/trip-create.ts` (지금 `TripCreatePage` · `TripRulesPage` 에 있는 코드를 옮기기만 한다):

```typescript
import { formatMonthDay } from '@/lib/trip-date'
import { kstDate } from '@/lib/trip-date'
import type { CategoryQuota } from '@/lib/recommend'

/** [TC-DATE] 기본 날짜 — 한국 날짜로 오늘 + 7일 */
export const defaultTripDate = () => kstDate(7)

/** [TC-TITLE] 자동 제목 — '(시군구 또는 시/도) 당일치기 MM-DD' */
export function defaultTripTitle(groupName: string, regionName: string | null, tripDate: string) {
  return `${regionName ?? groupName} 당일치기 ${formatMonthDay(tripDate)}`
}

/** [TC-TITLE-DUP] 내 여행에 같은 제목이 있으면 -01, -02 … */
export function dedupeTitle(base: string, existing: string[]) { /* 지금 코드 그대로 */ }

/** [TC-SEED] 자동 담기 구성 — 밥집 2 · 카페 1 · 명소 4 */
export const AUTO_ADD_QUOTA: CategoryQuota[] = [
  { category: 'babzip', count: 2 },
  { category: 'cafe', count: 1 },
  { category: 'spot', count: 4 },
]
```

### 3-2. 고정 규칙 ID — 문서와 코드를 grep 한 번으로 잇기

- 화면 문서의 규칙 표에 **ID 칸**을 더합니다: `| # | ID | 규칙 | 값 |` — 번호는 읽는 순서일 뿐이고 ID 는 바뀌지 않습니다.
- ID 는 `문서 약자-이름`: 새 여행 만들기 `TC-`, 홈 `HM-`, 지도 `MP-`, 추천 `RC-`, 동선 최적화 `RT-`, 장소 업데이트 `UP-`.
- 코드의 그 규칙 자리에 `[TC-TITLE]` 처럼 적습니다. `grep -rn "TC-TITLE" src supabase` 로 문서 → 코드, 코드 → 문서가 다 찾아집니다.
- 기존 TRIP-02-01 같은 기능 번호(요구사항 표)는 그대로 둡니다 — 화면 단위라 규칙까지 가리키지 못할 뿐입니다.
- **점검 스크립트**(`scripts/check-rule-ids.mjs`): 문서에 있는 ID 가 코드에 없거나, 코드의 ID 가 문서에 없으면 실패.
  커밋 전 · CI 에서 돌립니다.

### 3-3. 규칙 표 = 테스트

`vitest` 를 개발 의존성으로 더하고, 규칙 표의 줄을 그대로 테스트 이름으로 씁니다.

```typescript
// src/rules/trip-create.test.ts
test('[TC-TITLE-DUP] 같은 제목이 있으면 -01, 그것도 있으면 -02', () => {
  expect(dedupeTitle('강남구 당일치기 10-17', ['강남구 당일치기 10-17']))
    .toBe('강남구 당일치기 10-17-01')
})
test('[TC-DATE] 한국 시각 새벽 1시에도 +7일', () => { /* 시계를 고정하고 검사 */ })
```

먼저 쓸 곳: 자동 제목 · 중복 순번, 한국 날짜, 별점 점수 · 한 쪽 고르기, 자동 담기 구성, 최단 동선(2-opt 가 교차를 편다),
'+N' 묶기(확대해도 대표 유지), 화면 기억 만료.

### 3-4. SQL ↔ TS 두 벌 — 같은지 기계로 확인

- 저장소 밖에 있던 비교 스크립트를 `scripts/verify-sql-rules.mjs` 로 들입니다: 로컬 DB(`supabase start`)에 데모
  장소를 넣고, 같은 인자로 DB 함수와 앱 함수를 불러 쪽마다 비교합니다(추천 · 홈 · 가까운 100곳).
- 마이그레이션에서 DB 함수를 바꾸면 이 스크립트를 같은 커밋에서 돌립니다(`CLAUDE.md` 규칙으로).
- 상수는 한쪽에서만 정합니다 — SQL 이 받는 인자로 넘길 수 있는 것(반경 · 개수)은 앱이 넘기고, SQL 기본값은 같은 값으로.

### 3-5. 화면 기억 하나로

다섯 벌을 `src/lib/screen-memory.ts` 하나로 줄입니다.

```typescript
/** 앱을 켜 둔 동안 화면 상태를 기억 — ttl 이 지나거나 key 가 다르면 없는 것으로 */
export function screenMemory<T>(ttlMs: number) {
  let saved: { key: string; value: T; at: number } | null = null
  return {
    get: (key: string) => (saved && saved.key === key && Date.now() - saved.at < ttlMs ? saved.value : null),
    set: (key: string, value: T, at = Date.now()) => { saved = { key, value, at } },
    clear: () => { saved = null },
  }
}
```

화면은 `const feedMemory = screenMemory<Feed>(10 * 60 * 1000)` 처럼 만들고, 만료 시간은 규칙 파일의 상수(`[HM-REPICK]` 등)를 씁니다.

## 4. 진행 순서

| 단계 | 할 일 | 위험 | 확인 |
|---|---|---|---|
| 1 | ✅ 한국 날짜 `kstDate()` · `upcomingTrip()`(`trip-date.ts`) + 네 곳 교체 (**버그 수정**, 10/10) | 낮음 | 새벽 · 월말 · 연말 · 다른 시간대 기기에서 검사 |
| 2 | ✅ vitest 도입 · `src/rules/trip-create.ts` · `route.ts` 로 옮기기 · 테스트 29개(10/10). 두 문서 규칙 표에 ID 칸도 먼저 넣음 | 낮음 — 동작 그대로 | 타입 검사 · 테스트 · 데모 화면 |
| 3 | 규칙 ID 칸(문서) + 코드 표시 + `check-rule-ids` | 낮음 — 주석 · 문서만 | 점검 스크립트 |
| 4 | `screen-memory.ts` 로 다섯 벌 합치기 | 중간 — 돌아오기 동작 | 상세 다녀오기 화면 검사(지금 Playwright 시나리오) |
| 5 | `verify-sql-rules` 저장소에 들이기 | 낮음 | 로컬 DB 비교 통과 |
| 6 | 홈 · 추천 · 지도 규칙 파일 | 낮음 | 2단계와 같음 |

각 단계는 따로 커밋할 수 있고, 2 · 3 · 6 은 동작이 바뀌지 않습니다. 1 · 4 만 동작(버그 · 기억)이 바뀝니다.

## 5. 채택하면 `CLAUDE.md` 에 넣을 것

- 화면 규칙은 `src/rules/<문서 이름>.ts`, 여러 화면 공통은 `src/lib/`. 페이지 파일에 상수 · 판정 함수를 새로 두지 않는다.
- 규칙 표의 줄에는 고정 ID, 코드의 그 자리에 `[ID]`. 규칙을 바꾸면 문서 · 코드 · 테스트를 같은 커밋에서.
- DB 함수와 같은 규칙을 앱에도 둔 곳은 `scripts/verify-sql-rules.mjs` 를 돌린 뒤 커밋.
